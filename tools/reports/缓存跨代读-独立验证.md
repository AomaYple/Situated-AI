## 1. 验收①：跨代读（我自己摆的两代）

### 1.1 构造方法（不依赖任何既有用例的判据）

隔离目录里造两个**落在同一分片**、**内容等长**的文件（等长是关键：按旧偏移切出来的字节
正好是另一条**完整**条目），然后：

* **建**：`parse_cached(f1)`、`parse_cached(f2)`、`flush(force=True)` ⇒ 该片两条，各 375 B；
  索引 `{sig1: (0, 375, 1), sig2: (375, 375, 2)}`；
* **变体 B（真实两代）**：让写者重建数据段 —— 把 `_disk_load` 临时短路成 `None`（只在**我自己的
  harness 进程**里改，不动仓库代码）⇒ 同一路径被**重解析**、指纹不变、于是被重排到片尾
  ⇒ 第二代数据段 `{sig2 @0, sig1 @375}`；再把**第一代索引**覆盖回去 ⇒ 「旧索引 + 新数据」；
* **变体 A（确定性）**：索引里把 `sig1` 的位置改成第 2 条的位置，数据段不动；
* **读**：直接调 `_read_entry`（与 `_disk_load` 同一条走法）＋ 端到端 `parse_cached`。

### 1.2 读数

```
变体 B：第一代 idx sig1 = (0, 375, 1) → 第二代 idx sig1 = (375, 375, 1)；两代数据段不同 = True
        按第一代偏移在新数据上取 375 B、**原样解码**（= 没有闸门时的读法）
        = {'payload_sig': 'd1df0ebd54f4…', 'seq': 2, '值': …('S', '222')}     ← 另一棵树，且解压/反序列化都不报错
变体 A：索引里 sig1 → (375, 375, 2)（真实位置 (0, 375, 1)）
        该位置原样解码 = 上面那棵 '222' 的树
        _read_entry(索引给的 meta, sig1) = **None**                              ← 判否
交叉用「别人的 meta」去读：报未命中 1 · 读回自己的树 1 · **读回别人的树（即 failed）= 0**
端到端：parse_cached(f1) = ('S','111') = parse_file(f1) ✓ · 是否等于 f2 的树 = False ✓
        parse_cached(f2) = ('S','222') = parse_file(f2) ✓
```

⇒ **先证明陷阱是真的**（旧偏移切出的字节确实是一棵**合法**的另一棵树），**再证明闸门挡住了**
（判否 / 返回正确树，二选一，从不返回第三棵树）。**验收① 的口径满足：PASS。**

判据笔记（我自己踩的坑，写下来免得下一个人重踩）：我第一版 `dump()` 只摊 `Block`/`Scalar`、
不摊 `Assignment` 的 key/op 与 `Scalar.text`，于是「111 的树」和「222 的树」被判成**同一个元组**、
整条判据**恒真**。修正后才拿到上面这些读数 —— 任何「逐节点比对」的判据都要先自己反证一次。

## 2. 验收②：`_drop_shard_files` 只让写者删（读者 vs 写者，两进程，A/B）

**同一个负载，只差一处**：读者有没有删文件的权限。

* **臂 A（修复后语义）**：读者带真 `PYTEST_XDIST_WORKER=gw0` ⇒ 按设计只读；
* **臂 B（= 修复前语义，对照）**：同样的读者，但在它自己进程里把 `_is_xdist_worker` 钉成 `False`；
* 两臂各跑：写者（普通进程）连续重建分片 —— 每轮新增 2 个文件 + **强制重解析 1 条旧文件**
  （指纹不变、因此被重排到片尾 ⇒ **偏移整体移动**）；读者反复「抓索引视图 → 放一小会儿 →
  用**旧视图**去 `_disk_load`」并叠加「确定性投毒视图」；
* **外部采样器**每 250 ms 记一次盘上**落定的** `shard-*.bin/.idx` 文件数与字节数。

```
臂 A（读者只读）：读 512 次 · 命中 380 · _drop_shard_files 调用 **132** 次 ·
                 盘上文件数 min/首/末 = **30/30/32** · 字节 min/末 = 21,906/148,162 · **单调不减 = True**
                 写者：137 轮 / 重排 137 条 / 末 (32 文件, 148,162 B, 16 数据段)
臂 B（读者可删）：读 376 次 · 命中 363 · _drop_shard_files 调用 13 次 ·
                 盘上文件数 min/首/末 = **26/26/32** · 字节 min/末 = 20,813/135,960 · **单调不减 = False**
                 写者：136 轮 / 重排 136 条 / 末 (32 文件, 135,960 B, 16 数据段)
外部采样（0.25 s 间隔）：臂 A 30 → 32 一路只升；臂 B 出现 26 的低点（掉 6 个文件、非单调）
```

⇒ **读者在 132 次判坏里一次都没删**（臂 A 单调不减），而「读者可删」的对照臂**立刻出现缩减**
（方向与队长量到的「6 秒内 29→26 文件 / 9.14→3.65 MB」一致）。**验收② PASS。**

臂 A 的「只读」是**行为证明**而不是打印的标签：`_drop_shard_files` 的唯一分支就是
`if not _is_xdist_worker(): unlink`（`cache.py:447-449`），132 次判坏后文件数只增 ⇒ 该分支没走。

⚠️ 一处**实验设计错误**我当场改掉、也写在这里：第一版读者直接调 `_read_entry`，
于是 `_drop_shard_files` **一次都没被调用**（0 次）、两臂长得一模一样、实验等于没做。
判坏那条路在 `_disk_load` 里（`cache.py:483`）—— 撞修复必须撞**入口**，不能撞它的一个零件。

## 5. 验收④：反例 —— 「指纹相同、结果不同」，**它漏过去了**

### 5.1 构造（可复跑，仓库外）

1. `stale.txt` 写 `v = 111111\n`（12 B）→ `parse_cached` → `flush(force=True)`；记下 `mtime_ns` 与 `sig`；
2. **等长**改写为 `v = 222222\n`（仍 12 B），随后 `os.utime(p, ns=(atime_ns, 原 mtime_ns))` 把时间戳复原；
3. **新进程**（内存层空）读它，并与 `parse_file` 逐节点比对。
   内部对照：`control.txt` 做同样的等长改写、**不复原** mtime。

### 5.2 读数

```
stale.txt  改前 size 12 / sig 9e17a272d5f8222d…  改后 size 12 / sig **9e17a272d5f8222d…**（一字不变）
           · 内容真的变了 = True · size 相同 = True · **指纹相同 = True**
新进程：   缓存给的结果 = ('S','111111')      ← 旧树
           直接解析     = ('S','222222')      ← 真值
           与直接解析一致 = False · 等于**开跑前那棵树**（陈旧）= True
           真正解析过（未命中）的文件数 = **0**（0 ⇒ 答案来自磁盘层，不是重新解析）
           **是否漏过 = True**
对照 control.txt：指纹 3fcbfb8161a9743a… → f1e5169b079b2186…（变了）⇒ 读回 '222222'、未命中 1 次 ⇒ 正确
```

⇒ **差异确实来自「mtime 复原 + 等长」**，不是别的东西。

**定位实验（把「比了什么」钉死，非可达状态复现）**：我把该分片的数据段手工换成一个
`payload = (sig, 999999, 另一棵树)`、索引也指向它 —— `_read_entry` **照样接受**，返回那棵别的树。
⇒ 闸门比的是 **`payload[0] == sig` 这一个字段**。

### 5.3 最小定位（`cache.py` 的哪一行比较了什么）

| 位置 | 事实 |
|---|---|
| **`cache.py:428`** | `if not (isinstance(payload, tuple) and len(payload) == 3 and payload[0] == sig): return None` —— **只比 `payload[0]`（写入时的指纹）与调用方算出的 `sig`** |
| `cache.py:416` | `offset, length, _seq = meta` —— 索引里的**序号被丢掉**；`payload[1]`（序号）从头到尾**不参与比较**（定位实验：`seq=999999` 接受） |
| `cache.py:338-347` | `_signature()`：`sha256(f"{path}\0{st.st_mtime_ns}\0{st.st_size}\0{_engine_stamp()}")` —— **键里没有任何内容成分**；`:339` 的 docstring 却把它叫「**内容**指纹」（同行括号里自己写明是 路径+mtime+大小+引擎指纹） |
| `cache.py:48` | 模块文档「正确性」一节承诺：**「源文件一变，键就变」** ⇒ 与 E4 的反例直接冲突 |
| `tools/tests/test_cache.py:446-457` | `test_源文件一变缓存就失效` 把同一条性质钉成了用例，但它改写的样本**同时**改了 size（`alpha = 1\n` → `beta = 2\n`），因此只覆盖了安全的那一侧 |
| `cache.py:412` / `:555-556` | 措辞「判据用**内容自证**」「指纹是**读回来时的自证**」—— 实际自证的是**世代**（同一写盘来源），不是内容 |

**可达性（严重度判断，不夸大）**：
* **本仓工具链自己不制造这种状态**：全仓 `shutil.copy2` 只用在「原样备份 / 原样还原」
  （`console_probe.py:350/382`、`stage3_rerun.py:106/136`、`experiments.py:337/355`、`h1_probe.py:657`），
  还原后的内容与它被缓存时的内容**同源**，键相同也不会错。
* **真正要担心的是文件系统粒度**：键用的是 `st_mtime_ns`，但**有效分辨率是文件系统的**
  —— FAT/exFAT（2 s）、部分 SMB/网络盘的粒度远粗于 1 ns。在这种盘上，**同一 tick 内的等长改写**
  不需要任何人故意 `utime` 就会撞上同一把键。用户要求支持 Windows/Linux/macOS，游戏树又可以是外置/网络盘。
* ⇒ 定 **medium**：不是「今天就会错」，而是「这条性质被**当成结论**写在文档与用例里，而它有一个真实的反例」。

### 5.4 两条候选修法（成本写明，取舍不在我这层）

1. **≈0 成本（我推荐先做这条）**：把 `:412`/`:555-556`/`:339` 的措辞从「内容自证 / 内容指纹」
   改成「**世代自证 / 世代键**」，并在模块文档「正确性」一节**明写不覆盖的情形**：
   「**同路径、同 `mtime_ns`、同 `size` 而内容被改**（粗粒度文件系统、`copy2`/`utime` 复原时间戳）
   仍会命中旧条目；需要绝对正确时用 `V3_PARSE_CACHE=0` 或 `v3 cache --clear`」。
   同时给 `test_cache.py:446` 补一条「等长改写 + mtime 复原」的**已知边界**用例（标 `xfail` 或断言当前行为），
   免得下一个人把这条性质当结论。
2. **有成本**：把内容成分加进键（例如首 256 B + 尾 256 B + size 的摘要）。代价是**每次查键都要读盘**
   —— 磁盘层的命中路径会从「1 次 `stat`」变成「1 次 `stat` + 2 次小读」，**全量分析里这条路径是热点**
   （6,250 个文件 × 每次运行），必须先量命中路径的开销再决定。

**我没有把这条判成 blocker 的理由**（也写清楚）：修复原本要挡的那类失效（索引/数据错代 ⇒
静默换成另一棵树）**确实被挡住了**，而且我有 §1/§2 两组硬证据；漏过去的这一条是**另一条**通道，
它需要「键不变而内容变」这个前提。**但按 t54 合约第 4 条的原文（「若会漏过 ⇒ 判 needs_revision」），
判决就是 `needs_revision`。**
