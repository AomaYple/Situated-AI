# 2026-10-12 Mod 制作提速计划 2.2 重审（历史）

本页记录对 [Mod 制作提速实施计划 2.1](../design/exec/速度优化计划-正确性优先.md) 的重新审计和重排。重审基于提交 `7c67582` 及此前完整工程、实机和输入筛选证据；不改变产品目标、M1–M5 出口、正确性门禁、实机预算或生产开关。本页解释为什么改执行顺序，以及如何在不降低证据标准的前提下减少无效等待和返工。2.2 已作为历史执行批次封存，当前入口是[提速计划 2.3](../design/exec/速度优化计划-正确性优先.md)及[增量可玩版本重审](2026-10-12-增量可玩版本计划重审.md)。

## 重审结论

当前主要瓶颈已经不是 Python 工具、快照、完整测试或游戏自动化能否运行，而是取得第一组合法 M3 行为/质量配对的成本：现有检查点没有支持提名，战争仪器因缺少目标国家严格拒绝，M3-B 发起机会分母仍为 `null`。工程底座的完整 `n-auto` 已通过 3566 passed、21 skipped、1551 subtests；继续泛化工程优化不能自动产生产品机会。

2.1 的门禁本身正确，但执行结构仍有三个速度问题：

1. 输入资格、质量观测、候选实现和实机派发的前置关系分散在 R1–R9 中，容易在缺一个条件时启动整局。
2. 没有把“一组小型可判定试验”设为扩大预算前的硬门，阴性或不可测场景可能消耗过多时间后才停止。
3. 离线实现反馈、输入准备和真实游戏运行没有用明确车道隔离；可以并行的工作和必须串行的工作混在同一批次描述中。

因此 2.2 采用“准备包 → 单组试验 → 扩大验收”的漏斗，并把可并行的离线工作与必须串行的游戏工作分开。它减少无效启动和返工，不通过降低样本、窗口、质量或错误门禁来制造速度。

## 2.2 的执行结构

### 三条工作车道

| 车道 | 可做的工作 | 必须产出 | 互斥边界 |
|---|---|---|---|
| A：输入与资格准备 | 完整来源扫描、版本/DLC/挂载复核、机会筛选、质量观测契约、证据兼容性复核 | 一份可复核的 readiness packet，或带原因的停止包 | 不启动 Mod 处理臂；不把单国、命令合法或评分变化写成机会 |
| B：实现与离线反馈 | 单一财政/外部候选的数据源、生成器、定向契约测试、`modgen --check`、离线 baseline、文档解释 | 可部署候选及生成指纹，或明确否证 | 不改变真实实验输入；没有 A 车道的资格包不启动游戏 |
| C：实机与证据 | 控制先行、单组 pilot、行为/代价/质量读数、错误与恢复核对 | pilot 判定或完整失败包 | 始终使用 `RunLock`，游戏和正式性能测量串行；不与另一场实验争用安装、用户目录或存档 |

A、B 可以在不触碰游戏和正式证据的前提下并行；C 车道一次只允许一个游戏问题。任何车道都不能把自己的成功状态替代另一车道的出口。

### 四道速度门

1. **G0 静态准备门**：启动前一次性检查来源、版本、挂载、语言、DLC、输入 SHA、目的、质量字段、观测包和预算。任一项缺失就生成停止包，不启动游戏。
2. **G1 单组 pilot 门**：先跑一个控制/候选最小配对或一个明确的自然响应窗口。pilot 只回答“机会、响应和质量是否可测”，不计入正式样本数；缺机会、缺质量、出现同类错误或方向相反时立即停止该路线。
3. **G2 扩大门**：只有 G1 同时满足共同机会、单字段差异、实际响应、代价和最低质量观测，才登记主纲领要求的多组配对。任何扩大都必须在运行前冻结重复数、窗口、失败预算和反例。
4. **G3 M4 门**：M3 候选冻结后，先测匹配 vanilla 噪声，再执行早期/真实后期、长期、生命周期和性能出口。工具速度、模拟结果和单次安全实机不能跳过这一门。

### 最短可行闭环

当前只推进财政风险对第三方外交响应这一条闭环：

1. A 车道找新的完整无注入输入，并同时确认处理前风险/自然未决机会和质量读数。
2. B 车道只准备一个单字段候选；候选必须通过定向测试、生成一致性和离线门禁。
3. G0 通过后，C 车道先完成控制，再完成一个 pilot 候选配对。
4. G1 通过后才扩大到主纲领规定的跨国家和重复窗口；G1 未通过则记录否证，换接口或关闭路线。
5. G2 通过后进入 M4；政治、市场和其他扩展保持关闭。

这条路线不等待 M3-B 完整分母来阻塞独立的 M3-A，但也不把受控脚本机会写成自然发起证据。没有新输入、质量接口或机会定义时，A 车道直接停止，不重复 RUS/PRU 阴性世界和已耗尽战争预算。

## 速度如何测量

2.2 不预先承诺“提速多少”。每个批次记录以下指标，且把工程与游戏范围分开：

| 指标 | 口径 |
|---|---|
| 无效启动率 | 已启动游戏中因资格、挂载、输入、质量或错误门禁被拒绝的比例；分母和拒绝原因完整保留 |
| 修改反馈时间 | 单一修改到相关定向反馈、生成检查和必要完整回归的墙钟；不把无关测试混入 |
| 有效证据吞吐 | 从登记到第一组可判定 pilot、再到合格配对的总墙钟；没有合格配对时记为 `null` |
| 证据复用率 | 通过兼容性指纹复用的分析/控制材料数量及被迫重跑数量；不能把复制控制臂当重复样本 |
| 资源成本 | Python 分配、进程树 RSS、游戏 CPU/RSS、启动次数和磁盘输出分开记录 |

只有输入、环境、探针、窗口、输出和判据相同的 AB/BA 对照才可以计算速度或内存收益。新流程没有同语义旧流程时只记成本基线，不宣称倍数。

## 2.2 完成定义

计划重排完成不等于 Mod 完成。2.2 的执行改进只有在以下条件同时满足时才算验收：

- G0 能在游戏启动前拒绝缺资格、缺质量和缺来源的任务；
- G1 能以一组 pilot 明确推进、停止或换路线，不把阴性结果隐藏在长跑中；
- A/B/C 三条车道的输入、代码、游戏和证据互不污染，且运行锁与恢复门禁保持有效；
- 反馈时间、无效启动率、有效证据吞吐和资源成本有可复核记录；
- 所有 M3/M4 产品出口、错误分类、质量指标和生产开关保持原定义。

实施事实写入当前工作清单和 M3/M4 结果页；本页不写未来 SHA、不把计划落盘写成行为通过，也不以计划本身宣布整个 Mod 完成。
