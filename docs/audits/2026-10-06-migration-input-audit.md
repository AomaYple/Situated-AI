# M4 存档迁移输入盘点（2026-10-06）

## 目的

确认仓库现有实机证据中是否存在可以合法用于 `--allow-save-upgrade` 的跨版本 Victoria 3 存档。
盘点只读取有限存档头和 SHA-256，不改写、不重打包、不修改版本字段，也不把升级开关本身当成迁移成功。

## 可复现命令

在仓库根目录使用仓库虚拟环境运行：

```text
.venv\Scripts\python.exe tools\probe\save_migration_audit.py --root tools\out --output tools\out\decisions\migration-audit-20261006.json
```

工具会递归读取 `*.v3`，保留相对 POSIX 路径、有限头字段和完整 SHA-256；解析失败也会留在报告中，退出码为 1。
报告位于被 `.gitignore` 排除的 `tools/out/`，本页保存可审计的摘要。

| 项目 | 结果 |
|---|---:|
| 存档文件总数 | 9 |
| 版本 | 全部 `1.14.5` |
| 解析错误 | 0 |
| 跨当前版本输入 | 0 |
| 可用于升级实验的输入 | 0 |
| 观察者存档 | 9 |
| 含空游戏规则引用 | 1 |
| 已停用 Mod 状态标记 | 0 |

9 个文件的日期范围是 `1836.4.1` 至 `1840.7.1`，它们都是同一游戏版本下的检查点。
含空游戏规则引用的文件仍保留其 SHA 和头信息，但不能作为干净升级输入；它也不改变“没有跨版本输入”的结论。

## 结果：当前用户存档目录

随后对当前机器的 `Victoria 3/save games` 目录做了同样的只读盘点。这里有 5 个 `.v3`：4 个是 `1.14.5` 且带空游戏规则引用，
另 1 个 `TEST_FAIL_law_changed_1841年1月2日.v3` 是 `1.14.4` 观察者存档。这个跨版本文件的完整 SHA-256 是
`e4a926f0c96f448c619d60de4a8f0b84da24727d5ecab962e011f5f4065f1f8d`，但它包含 `setting_sitai_*`、`je_sitai_*` 和旧九国
`sitai_*` 状态标记，所以可升级输入数仍为 0。

在启动前门禁加入旧状态标记之前，曾用这个原始文件做过一次明确声明 `--allow-save-upgrade` 的真实尝试，证据为
`tools/out/decisions/stability/vanilla/20261005-192152`。它确实载入到 `1841.3.2.12` 并推进到 `1841.4.3.6`，
但产生 `Script system error! = 598`、`Assertion failed = 1`，且日志记录了大量旧 `je_sitai_*` / `sitai_ru_*` 引用，
严格门禁拒绝通过。这个失败证明版本升级开关不能清理旧 Mod 状态，也不能把旧世界直接当成新生产逻辑的输入。

现在 `save_header` 会在有限启动前检查中标记这些旧状态，`validate_load_save_header` 会在任何游戏进程启动前拒绝它们；
迁移审计报告的 `legacy_mod_state` 字段和 `eligible_upgrade_inputs` 字段会保留这一判定。
修复后的同一命令已复跑，证据为 `tools/out/decisions/stability/vanilla/20261005-193432`：在启动游戏前以
`ValueError: 存档包含已停用 Mod 状态` 退出，`progress=null` 且 `cleanup_errors=[]`，没有再次制造引擎错误。

## 出口与后续

M4 的迁移专项完成了输入盘点、旧状态识别和启动前门禁，但跨版本迁移仍未验证。`--allow-save-upgrade` 只允许显式越过版本不一致的启动前拒绝，
并不替游戏完成存档升级；当前唯一跨版本候选因旧 Mod 状态残留被拒绝，真实跨版本成功结果仍不存在。

只有获得由游戏真实产生、版本不同于当前安装、观察者状态有效且不含空规则的原始 `.v3`，才可以继续运行升级实验。
实验必须保留原始字节、完整 SHA、实际载入日期、错误门禁、挂载和收尾证据；在此之前不能把同版本重载、改写头字段或模拟报告写成迁移通过。
