**三条最重要的横向结论**（详见各节）：

1. **本地化键名几乎总是「等于定义键」**：特质、角色、互动、概念、修正符类型的 `.yml` 键就是 `.txt` 里的键名。这是内容 mod 最容易踩坑的地方（见 §22.1 与 §24）。
2. **官方 `.md` 有相当比例的字段是文档遗留或未使用**，必须交叉验证 —— 例如 `eras.md` 的 `start_date`/`end_date`/`icon` 在 1.14.2 的 `00_eras.txt` 里**一个都没用**；`trigger_localization.md` 里的示例触发器名（`is_betrothed`、`dread`、`any_child`）在 V3 里**全部不存在**（那些是 CK3 的名字）。
3. **动态文本与提示是「两套独立机制」**：`customizable_localization`（主动从 loc 里选一段文本）vs `effect_localization` / `trigger_localization`（属于效果/触发器的固定提示）。做内容 mod 时前者用得多得多。

## 1. `character_templates` —— 历史人物库

### 1.1 用途

定义**具名历史角色**的生成模板。游戏在开局、角色池补充、兴趣集团领袖选举、指挥官招募、摄政选择等时机，从这里挑模板造人。
`GAME\common\character_templates\` —— **210 个 .txt / 1,983 个顶层键 / 1,233,202 B**。这是本篇体积最大的目录。

### 1.5 覆盖 vs 新增

| 目标 | 做法 | 注意 |
|---|---|---|
| **新增一个历史人物** | 在 mod 的 `common\character_templates\` 下新建任意 `.txt`，写一个**新键名**的模板 | 键名全局唯一即可；建议沿用 `TAG_名_姓` 或 `<tag>_<name>_character_template` 惯例 |
| **改原版人物的属性** | 用**同一键名**重写整个模板块 | 块级替换，不是字段级合并 —— 必须把要保留的字段全部抄回来 |
| **删除原版人物** | 无官方「删除」机制 | 可行做法是把该模板的 `*_usage` 触发器改成 `always = no`，或把 `possible` 之类的入口堵死【推断，未实测】 |
| **让新人物必定出现** | usage 块里**不写 `chance`** | 源码注释明确：不写 = guaranteed to spawn if possible |
| **让新人物按概率出现** | usage 块里写 `chance = <0-100>` | 见 `historical_leaders_europe.txt:84` 的 `chance = 20` |

### 1.6 实战提示

1. **新增历史人物的最小步骤**（这是本篇最实用的流程）：
   1. 建 `common\character_templates\my_character.txt`，写模板（键名如 `my_mod_napoleon_iv`）。
   2. 名字若用自定义 loc 键（如 `Napoleon_IV`），必须在**某个** `localization\<lang>\*.yml` 里补 ` Napoleon_IV:0 "Napoleon IV"` —— 名字在 V3 里就是普通 loc 键（实证：`localization\english\names_l_english.yml` 里有 ` Georges:0 "Georges"`）。也可以直接复用文化名库里已有的键，或用 `first_name = culture` 走随机。
   3. 给 `dna = <key>` 的话，必须在 `common\dna_data\` 下建同名键（见 §2.3）。**不想做 DNA 就写 `dna = random`**。
   4. 至少给一个「入口」：`ruler = yes` / `ig_leader = yes` / `is_general = yes` / `is_agitator = yes` / `role = <角色键>`，**或者**配置一个 `*_usage` 块（推荐，可控性最高）。
   5. 想让他「只在某国出现」→ `*_usage.country_trigger` 里写 `c:TAG ?= THIS`。
   6. 想让他「只在某年之后出现」→ `earliest_usage_date` / `latest_usage_date`。
2. **`traits = { ... }` + `trait_generation = { }` 是一对**：原版绝大多数「手工设计」的角色都写成 `traits = { A B C }` 紧跟 `trait_generation = { }`。**空块不是没写**，而是显式关闭随机特质生成，保证人物特质完全可控。不写 `trait_generation` 会继承 `default` 模板那一大坨随机逻辑（`00_default_template.txt:22-81`，含 `add_random_trait = personality/skill/condition`、`add_experience`、按年龄判定等）。详见 §1.4（B）与 §1.7。
3. **不要把 `role = character_role_politician` 和 `politician = yes` 混用理解**。1.12 起官方注释（`00_default_template.txt:4-7` 逐字）区分了三种写法：
   ```text
   # As of 1.12, there's a few different ways to specify roles, all of these can be mixed together so long as the roles are compatible
   # ruler = yes, heir = yes, executive = yes etc - old method, works as before as a shortcut to assign the archetype and its associated auto-assigned roles
   # role = ruler/heir/agitator/politician/executive/general/admiral/other - assigns the archetype and its associated auto-assigned roles
   # role = <database key> - assigns role from database + any archetype auto-assigned roles
   ```
4. **`age` vs `birth_date`**：`country_arg.txt:114` 有 `age = 57 # Born in 1779, exact birthdate unknown`。用 `age` 的人**不会随时间变老**（无生日），适合「史实生日不明」的人物 —— 但也意味着游戏后期他还活着。
5. **`home_region` 决定 `religion = random` / `culture = random` 的抽样基准**（官方注释明说 `If home region is specified, random is based on home state, otherwise home country`）。想让人物出现在正确的地方，别省这个字段。
6. **无 `.md` 文档**：`character_templates` 没有官方字段文档，本篇的 32 个字段是机械提取 + 注释归纳的结果。写新字段前**务必先在原版 210 个文件里 grep 一遍**确认字段名存在。

### 1.7 `default` 模板的 `trait_generation`（逐字引用，重要）

`GAME\common\character_templates\00_default_template.txt:22-81` —— 这是理解「历史人物为什么特质不一样」的关键：

```text
	trait_generation = { 		# this effect will run as soon as the character is created (should only be used for traits)
		if = {
			limit = {
				trait_value > 0
			}
			set_variable = has_historical_traits
			add_experience = trait_value
		}
		else = {
			add_experience = 4
		}

		if = {
			limit = {
				is_adult = no
			}
			add_trait = trait_child
		}
		if = {
			limit = {
				is_adult = yes
				trait_value = 0
			}
			add_random_trait = personality
			if = {
				limit = {
					OR = {
						NOT = { has_variable = has_historical_traits }
						trait_value <= 3
					}
				}
				add_random_trait = skill
			}
		}

		if = {
			limit = {
				age >= 45
				trait_value < 8
			}
			random_list = {
				33 = {}
				33 = { add_experience = 1 }
				33 = {
					add_experience = 2
					add_random_trait = skill
				}
			}
		}
		if = {
			limit = {
				age >= 30
				NOT = { has_variable = has_historical_traits }
			}
			random_list = {
				95 = {}
				5 = { add_random_trait = condition }
			}
		}
	}
```

**要点**：`trait_value` 是引擎内置的「角色特质总价值」，由角色已拥有的各特质的 `value` 字段求和得到（见 §1.8）。当 `trait_value > 0` 时设 `has_historical_traits` 变量 —— 之后的年龄判定会因此**跳过额外随机特质**。这就是「手工给了 traits 的历史人物不会被随机塞一堆性格」的机制来源。

相关 `defines`（`GAME\common\defines\00_defines.txt`）：

```text
1915: ### TRAIT GENERATION
1916: # Every week, a character's Expected Trait Value meter increases by the specified amount below depending on their role and what they're doing (Commanders also gain the Activity Level from their Orders)
1917: # Every week, a percentile die is rolled against ( Expected Trait Value meter - Current Trait Value . If the die rolls under the current value, a new random trait will be added, if a valid one exists.
1920: MAX_EXPECTED_TRAIT_VALUE = 12.0					# The maximum amount of Trait Value a character can develop normally (note: not adhered to by add_trait effect)
1921: MAX_TRAITS_PERSONALITY = 2						# The max amount of Personality Traits a character can develop normally (note: not adhered to by add_trait effect)
1922: MAX_TRAITS_SKILL = 2							# The max amount of Skill Traits a character can develop normally (note: not adhered to by add_trait effect)
1923: MAX_TRAITS_CONDITION = 2						# The max amount of Condition Traits a character can develop normally (note: not adhered to by add_trait effect)
1925: TRAIT_GAIN_DIVISOR = 100.0						# Final trait gain is always divided by this so we don't have to use all the decimals
```

| 目标 | 做法 | 注意 |
|---|---|---|
| **新增特质** | 新键名 + **必须**补 loc 键 | loc 文件：`GAME\localization\<lang>\character\character_traits_l_<lang>.yml`；键名 = 特质键名，形如 ` alcoholic:0 "Alcoholic"` |

### 2.6 实战提示

1. **新增特质的三件套（缺一必炸）**：① `common\character_traits\*.txt` 里的定义；② `localization\<lang>\character\character_traits_l_<lang>.yml` 里的同键名文本；③ `texture` 指向的 `.dds`（可先复用原版图标路径）。
2. **`type` 决定随机获取行为**：`personality` / `skill` / `condition` 各受 `MAX_TRAITS_PERSONALITY` / `MAX_TRAITS_SKILL` / `MAX_TRAITS_CONDITION` = 2 限制（`00_defines.txt:1921-1923`）。想让新特质容易被随机抽到，把 `type` 设对并调高 `weight`。
3. **`possible` 只影响「随机获得」**，不影响已有特质（`.md` 原文：`Does NOT impact the validity of the trait once it's acquired`）。要让特质永远不能同时存在，用 `replace`。
4. **`value` 影响 trait_value 预算**：`value` 越大，角色被判定为「特质已够多」越早。原版 `reserved` 用 `value = 3`。`00_defines.txt:1920` 的 `MAX_EXPECTED_TRAIT_VALUE = 12.0` 是上限。
5. **孤儿特质**：`trait_child` 定义在 `personality_traits.txt:3`，被 `00_default_template.txt` 的 `trait_generation` 用 `add_trait = trait_child` 硬编码引用；`00_defines.txt:1903` 有 `CHILD_TRAIT = "trait_child"`。**不要删它**。
6. **`country_modifier` 只在本人是国家统治者时生效**，`interest_group_modifier` 只在本人是 IG 领袖时生效 —— 想让特质对「任何持有者」都有效，用 `character_modifier`。

| **改头衔显示** | 同键名重写；或改 `title_format = custom` + 提供 loc 键 `<角色键>_custom_loc` | `.md` 逐字：`If set to custom, a customizable localization with the format key_custom_loc (example: character_role_politician_custom_loc) must be added to the customizable loc database.` |
| **删除角色** | 无官方机制 | 未确认 |
| **改角色池补充** | `pool_spawn_target_*` / `pool_spawn_target_country_wide` | 两者互斥；`.md` 警告：`WARNING: Using complex script values here is likely to degrade performance!` |

### 3.6 实战提示

1. **`title_format = custom` 是一条通向 `customizable_localization` 的硬连接**：`character_role_politician_custom_loc` 这个键**不存在于原版**（原版 `politician` 用的是 `from_name`），但 `character_role_magnate` 用了 `custom`。要自定义头衔走这条路，见 §6.1。
2. **角色的 loc 键在 `localization\english\characters_l_english.yml`**，实测条目：
   ```text
   character_role_ig_leader: "[concept_leader]"
   character_role_magnate: "[concept_magnate]"
   character_role_other: "Other"
   ```
   注意：值可以是**概念引用**（`[concept_xxx]`），不一定是纯文本。
3. **`auto_assigned = yes` 会让所有该原型的新角色自动获得此角色**。想让角色只有脚本能加，**不要写 `auto_assigned`**（`.md` 明说 `Roles do not need to have archetypes if they are fully controlled by script`）。
4. **`priority` 决定「主头衔」**：数值越大越可能成为角色卡上显示的 `GetPrimaryRoleTitle`（`characters_l_english.yml` 与事件 loc 大量使用）。原版：ruler 100 > heir 99 > general/admiral 50 = emperor_of_japan 50 > ig_leader 25 > executive/magnate 10 > agitator 2 > politician 1。
5. **`career_length = { min max }` 只对 `on_career_end` 有意义的角色必要**。原版：general/admiral `{ 15 30 }`、executive/agitator `{ 10 20 }`、politician `{ 5 10 }`。

### 4.6 实战提示

1. **loc 键后缀实测**（对 `character_interactions_l_english.yml` 机械统计，47 个条目）：`_desc` × 3、`_info` × 9、`_title` × 0，**其余是裸键名**。所以最小要求只有裸键名。
   实测示例（逐字）：
   ```text
   grant_command_to_ruler: "Grant Command"
   abdicate_monarch: "Abdicate the Throne"
   abdicate_monarch_info: "The [concept_ruler] will abdicate the throne of [Character.GetCountry.GetName], passing the role of [Character.GetPrimaryRoleTitle] to [Character.GetHerHis] [concept_heir]"
   ```

3. **`cooldown` 是脚本化时长**，实测两种写法：`cooldown = { days = normal_modifier_time }`（用引擎脚本值）和 `cooldown = { years = 15 }`。UI 通过 `CharacterInteraction.GetCooldownDuration` 显示，loc 键是 `CHARACTER_INTERACTION_COOLDOWN_DURATION_INFO_IMPL`（已存在，无需新增）。

## 5. 重点：`character_templates` × `character_traits` × `character_roles` × `character_interactions` 如何配合

这是四个目录里**唯一需要串起来理解**的部分。下图是「造一个历史人物」时四者的数据流：

```
character_roles                 character_templates              character_traits
──────────────                  ───────────────────              ────────────────
character_role_ruler ──┐         role = character_role_ruler ──►  traits = { A B C }  ──► 值来自
character_role_heir  ──┤              │                          trait_generation = {}      type / value
character_role_general┤              │  auto_assigned = yes            │                  character_modifier
character_role_...   ──┘              ▼                                 ▼                  replace / weight
                                角色初始化（开局 / 池补 / 任命）   引擎算出 trait_value
                                        │
                                        ├──► commander_usage { role = general }  ──► 需要角色有 general 原型
                                        ├──► interest_group_leader_usage         ──► 需要 IG 存在且非 marginal
                                        └──► agitator_usage / executive_usage

                                        ▼
                              character_interactions（玩家/AI 对已存在的角色动手）
                              grant_command_to_ruler  ──effect──►  add_character_role = general
                              remove_command_from_ruler ─effect─►  remove_character_role = general
```

### 5.1 四条实测的耦合规则

**规则 1：`character_roles` 的 `type`（archetype）是 `character_templates` 里 `*_usage.role` 的合法域。**

- `commander_usage.role` 实测取值只有 `general` / `admiral`（`country_arg.txt` 全篇）。
- `commander_usage` 在角色定义里**从不与 `is_general = yes` / `is_admiral = yes` 同时出现**在同一人物上——它是「将来某个时点才让他成为将军」的**延迟指派**通道；`is_general = yes` 是「开局就是将军」。
  实证：`country_arg.txt:653` 的 `ARG_lucio_norberto_mansilla` 有 `is_general = yes` + `commander_usage`；`:694` 的 `ARG_bartolome_mitre` 只有 `commander_usage`（依赖 `earliest_usage_date = 1859.1.1` 才出场）。

**规则 2：`character_roles.auto_assigned = yes` 决定了「`role = <archetype>` 会自动带上哪些角色，以及哪些角色能出现在 `character_interactions` 的判定里。**

`grant_command_to_ruler` 的 `potential` 逐字用了 `has_role_of_type = general` / `has_role_of_type = admiral` / `is_ruler_of_own_country`。这些**全部是 `character_roles` 里 `type = ...` 的值**，不是 `character_traits` 的东西。所以：

- 新增一个 `type = general` 是**不可能**的（`type` 是硬编码原型枚举，不是数据库键）。
- 想加「新职位」只能加 `character_role_xxx` 并给它一个**已有原型**（或 `other`），然后用 `has_role_of_type` / `has_role = character_role_xxx` 在脚本里区分。

**规则 3：`character_traits` 的 `possible` 是「能不能随机长出来」的闸门，不是「能不能被给予」的闸门。**

所以 `character_templates` 里 `traits = { ... }` 可以直接给出一个 `possible` 不满足的特质（例如给非鼓动家角色一个 `possible = { NOT = { has_role_of_type = agitator } }` 的特质）。这是**故意留的**——`.md` 原文：`Does NOT impact the validity of the trait once it's acquired`。

**规则 4：`character_interactions` 是「运行期改变角色角色/特质」的唯一脚本入口。**

实测 `00_character_interactions.txt` 的 `effect` 里出现的效果：

```text
grant_command_to_ruler            effect = { add_character_role = general }
remove_command_from_ruler         effect = { remove_character_role = general }
```

这两个效果的提示文本由 **`effect_localization`** 提供（见 §6.2），而它们的 loc 键是 `ADD_CHARACTER_ROLE` / `REMOVE_CHARACTER_ROLE`（在 `localization\english\effects_l_english.yml`）。

### 5.2 新增一个历史人物的完整清单（跨 4 个目录 + 2 个 loc 文件）

| 步骤 | 目录 / 文件 | 内容 | 是否必需 |
|---|---|---|---|
| 1 | `common\character_templates\<任意名>.txt` | 模板块，键名唯一 | ✅ 必需 |
| 2 | `common\dna_data\<任意名>.txt` | `dna_<x> = { portrait_info = { genes = { ... } } }` | 想要固定长相则必需；否则 `dna = random` |
| 3 | `localization\<lang>\character\character_traits_l_<lang>.yml` 等 | 只在你**新造**了特质/角色时才需要 | 视情况 |
| 4 | `localization\<lang>\names_l_english.yml`（或任意 `.yml`） | 姓名 loc 键（` Napoleon_IV:0 "Napoleon IV"`） | 用自定义姓名字面量时必需 |
| 5 | （可选）`common\character_traits\*.txt` | 给这个人物专属的特质 | 可选 |
| 6 | （可选）`common\character_roles\*.txt` | 给这个人物专属的职位 | 可选 |

> 实证：原版 `fra_clemenceau_character_template` 、`ARG_Juan_Manuel_de_Rosas`、`dna_georges_clemenceau`、`dna_abraham_lincoln` **都没有同名 loc 键**（已用 grep 确认）。这说明：**模板键名、DNA 键名本身不需要 loc 条目**；需要 loc 的只有「姓名、特质名、角色名、互动名」这类**会显示给人看的**东西。

### 6.5 覆盖 vs 新增

| 目标 | 做法 | 注意 |
|---|---|---|
| **新增 morph 基因** | 在 `morph_genes` 里加新 `gene_xxx`，`index` 必须全局唯一（DNA 字符串按 index 定位） | ⚠️ **高危**：DNA 是**按 index 序列化**的。插队会破坏所有原版 DNA。**必须追加在末尾** |
| **新增饰品槽位** | 在 `accessory_genes` / `special_genes` 里加新槽位 | 新槽位**不会**出现在原版 DNA 里，需要自己给所有相关 DNA 补值，否则取不到 |
| **改原版基因取值** | 同键名重写 | 会影响所有使用该基因的族群外观（全局） |
| **新增贴花** | 在 `gene_face_dacals` 或 `special_genes.morph_genes.decals` 里加条目 | 需要 `gfx\models\portraits\decals\...` 下的 `.dds` 三件套（diffuse/normal/properties） |

### 6.6 实战提示

1. **`index` 是硬约束，不是装饰**。`dna_data` 里的 DNA 字符串按 index 定位每个基因的取值（见 §8）。**修改 `index` 会静默破坏原版所有 DNA**。
2. **`genes.md` 的可信度很低**。它 21 行、自称 `very incomplete`，且 `decal` 的 `type` / `atlas_pos` / `alpha_curve` 三个字段在 1.14.2 的 8 个 `.txt` 里**一个都没有出现**。真正的字段是 `body_part` / `textures` / `blend_modes` / `priority` / `age`。**以 `.txt` 为准**。
3. **`@maleMin` / `@femaleBsMax` 这类 `@` 常量是文件级宏**（`01_genes_morph.txt:1-19` 定义了 19 个），只在**同文件内**有效。
4. **`special_genes` ≠ `accessory_genes`**：前者不进 DNA，只能被硬编码引用。想让新饰品能被玩家在 DNA 里指定，**别**放 `special_genes`。
5. **`female = male` 是别名赋值**，不是在给 female 定义一个叫 "male" 的值 —— 解析器会复制 `male` 块的内容。原版大量使用以省字节。

数值范围实测 **0–255**（`255` 出现频繁，`gene_complexion={ "complexion_01" 0 "complexion_01" 0 }` 为 0）。**前一半 = 显性基因，后一半 = 隐性基因**——这与 `genes.md` 里 `blend_range` 的 `"dominant"` / `"recessive"` 描述一致，也对应 `00_defines.txt` 的：

```text
1910: INHERIT_RECESSIVE_GENE_CHANCE = 0.25 # Probability of a recessive gene being picked as an heir's dominant/recessive gene. Only used for portraits.
```

### 8.5 覆盖 vs 新增

| 目标 | 做法 | 注意 |
|---|---|---|
| **新增具名 DNA** | 新键名 `dna_<x> = { portrait_info = { genes = { ... } } enabled = yes }` | 文件名可任意（原版惯例 `00_<name>.txt`） |
| **改原版历史人物长相** | 同键名重写 | 只改数字即可保留其余字段（但要抄全整个 `genes` 块） |
| **半手动造 DNA** | **未确认**是否有官方工具 | 原版做法看起来是游戏内肖像编辑器导出 |

### 8.6 实战提示

1. **`.md` 的 `dna = ""` 已经过时**：1.14.2 的 583 个 DNA 文件里 `dna =` 出现 **0 次**，`portrait_info` 出现 583 次。**只写 `portrait_info`**。
2. **`enabled = yes` 有 546/583 个文件写了**（37 个没写）。既然绝大多数都写，**建议照写**。
3. **最省事的做法是复制一个体型/性别相近的原版文件，改名 + 改键名**。基因键名必须与 `genes` 里的槽位/基因名**完全一致**，否则该行会被静默忽略。

5. **不写 DNA = 用 `dna = random`**。`character_templates` 的 `00_default_template.txt:18` 逐字：`dna = random # Generate random dna from a random ethnicity in the culture`。

### 9.6 实战提示

1. **`list "<名字>"` 是 CoA 系统的核心「变量」语法**。它出现在 `texture`、`pattern`、`colorN`、`instance` 的位置上，表示「从该池中按权重抽一个」。实测被引用的池名包括 `charge`、`normal_colors`、`metal_colors`、`pattern_anarchy`、`chartered_companies_charges`、`power_bloc_shield` / `_top` / `_frame` / `_center` / `_side` / `_colors`。
2. **颜色槽可以互相引用**：`color1 = color2` 表示「取本块 `color2` 的值」。这是给同一纹章做配色联动的常用手法（见样本 D）。
3. **`sub = { parent = "..." }` 是复用机制**。`01_subs.txt` 里 86 个 `sub_*` 就是被各国纹章组合使用的零件库。**做新国旗时优先找现成 `sub_*` 叠加**，比从头画省力。
4. **`@` 宏 + `@[...]` 表达式**在 CoA 里用得很重（`@third = @[1/3]`、`@canton_scale_cross_x = @[ ( 333 / 768 ) + 0.001 ]`）。`@[...]` 是**算术表达式**，可以引用同文件的其它 `@` 宏。
5. **改 `03_random_power_bloc.txt` 的图层顺序会崩**。源码注释逐字警告：`# If we ever change the order of layers here, remember to also update them in NGraphics::NPowerBlocCoa::PIECE_LAYERS_ORDER.` 同样的话在 `instance` 的 `scale` / `position` 上也出现（`# when changing this remember to update NPowerBlocCoa in 00_defines.txt`）。
6. **`02_overlord_border.txt` 是空块**（内容全被注释）—— 说明「宗主国边角」功能在 1.14.2 被停用了。**未确认**是临时还是永久。

> 注意：**纹章画布是 768×512**（与 `options\atlases.txt` 里最小的 `48 32`、最大的 `512 512` 都不同 —— 那是图集 tile 尺寸，不是单张纹章尺寸）。

### 10.5 覆盖 vs 新增

| 目标 | 做法 | 注意 |
|---|---|---|
| **给新 TAG 一个旗帜** | 新建列表 `<TAG> = { flag_definition = { coa = <纹章键> } }`；或干脆什么都不写（回退用 TAG 本身当 CoA key） | 文档逐字：`if no flag definition is applicable for a country then its tag is used a COA_KEY` |
| **改某国国旗** | 覆盖对应的 `<TAG>` 列表块，加一条 `priority` 更高的 `flag_definition` | 或者直接改 `coat_of_arms`（更简单，见 §9.5） |
| **追加而非替换某国列表** | 用 `includes = <另一个列表>` | 唯一的两处原版用例是 `GER` 和 `TRI` |

### 10.6 实战提示

1. **`DEFAULT` 是始终参与的**（文档逐字：`the DEFAULT list is always included`）。所以给 `DEFAULT` 加高 `priority` 的 `flag_definition` 会影响**所有**国家。**慎用**。
2. **`coa = list "<池名>"` 也可以**（文档里的 `[list] COA_KEY`），即「从模板池里随机抽一个纹章」。原版 `DEFAULT` 的第一条就用 `coa = list "chartered_company"`。
3. **`priority` 决定胜负**（文档逐字：`valid flag definition with the highest priority applies`）。实测 `DEFAULT` 里用 `priority = 1000` 做兜底。
4. **给附属国加角标只需两个字段**：`allow_overlord_canton = yes` + `overlord_canton_scale` / `overlord_canton_offset` 调位置。
5. **改旗子有两条路**：改 `flag_definitions`（管绑定）或改 `coat_of_arms`（管图案）。**改图案通常更简单**。

### 11.5 覆盖与新增（本节四个目录）

| 目录 | 新增 | 覆盖 | loc 要求 |
|---|---|---|---|
| `dynamic_country_names` | 新 `dynamic_country_name` 条目（可放任意 TAG 块或 `DEFAULT`） | 同 TAG 块重写 | `name` / `adjective` 指向的 loc 键必须在 `.yml` 里存在 |

| `dynamic_country_map_colors` | 新键名 | 同键名重写 | 无（`color` 是 `named_colors` 的键） |
| `named_colors` | 新颜色名 | 同键名重写 | 无 |

**实战提示**：

1. **`dynamic_country_map_colors` 的注释给了硬规则**：`you /must/ check that a tag exists before doing anything else`（`exists = c:XXX` 必须在最前面）。这是防止访问不存在的国家导致崩溃。
2. **`dynamic_country_names` 的 `priority` 相同则「文件里靠前者优先」**（`.md` 逐字：`If same priority, first one in file is used`）。这是**与多数 V3 系统相反**的规则（多数是后者覆盖），务必注意。
3. **`named_colors` 是纯调色板，不参与任何逻辑**。改它会影响**所有**引用该色的地方（旗帜、地图、商品、编队）。
4. **`dynamic_treaty_names` 的 `weight` 是「绝对权重」**（`readme.md` 逐字：`Names with higher weights are more likely to be picked`），不是百分比。

| **新增科技** | 在 `common\technology\technologies\` 下新建 `.txt`，写新键名定义 | **必须**补 loc 键：`<科技键>`（名称）、`<科技键>_desc`（描述）。`modifier` 里引用的修正符类型必须已在 `modifier_type_definitions` 里定义（见 §6.4） |
| **改原版科技** | 同键名重写 | 块级替换 |
| **改时代成本** | 同键名重写 `era_N` | 会影响所有该时代科技的研究成本，**全局** |
| **加新科技时代** | 新键名 `era_6` | **未确认**引擎是否支持第 6 个时代（`00_eras.txt` 只有 5 个，UI 的科技树分页可能硬编码 5 列） |

### 13.6 实战提示

1. **`unlocking_technologies` 语义容易搞反**：它列的是**前置**（`line_infantry` 需要先有 `mandatory_service` 和 `military_drill`），不是「本科技解锁了谁」。名字有误导性。
2. **`can_research = no` 造「只能扩散获得」的科技**。原版 `sericulture` 用它 —— 注释还说明它解锁 Rice Farms 的 Mulberry Groves PM。
3. **`modifier` 里只能写 `modifier_type_definitions` 里已定义的键**。这是 §6.4 与本节之间最重要的耦合：**新增科技若要用新修正符，必须先新增修正符类型**。
4. **时代成本改动会影响「进度加成」的换算**。`00_eras.txt` 注释逐字提醒：`for progress bonuses, use an approximate third`，并要求同步更新 `events` 与 `journal_entries` 里的进度加成（那些不在本篇范围）。
5. **`eras.md` 不可信**：`start_date` / `end_date` / `icon` 三个字段在原版 5 个时代里出现 **0 次**。若你要新增 `era_6`，别指望这三项能起作用 —— 先把 `technology_cost` 写好再测试。
6. **科技效果通过 `modifier` 影响国家**，因此它的定位提示文本来自 `modifier_type_definitions` 的 `decimals` / `color` / `percent` / `prefix` / `suffix` 字段（见 §6.4）。

### 14.7 实战提示

1. **`common\` 里的概念定义几乎是空的，真正的文本 99% 在 `.yml`**。所以「加一个新概念」的**主要工作量在写文本**，不在写脚本。
2. **`_desc` 才是悬停框正文**，`concept_x` 是标题。只写一个的话，悬停框会缺一半。原版 612 个概念里有 614 个 `_desc`（比概念数还多 2，说明有 2 个 `_desc` 没有对应概念 —— 可能是遗留）。
3. **正文里可以嵌套概念引用**（`concept_regime_change_desc` 里就引用了 `[concept_government]` 和 `[Concept('concept_law', ...)]`）。这形成「概念网络」，是 Vickypedia 的核心体验。
4. **`[Concept('key', 'display')]` 是显示文本覆盖**，做「同一概念在不同语境显示不同词」的正规手段。
5. **`concepts_l_english.yml` 头部那批 `*_GC_LINK` / `*_INGAME_LINK` 是「主菜单里打开 Vickypedia 会崩溃」的规避写法**（注释逐字：`this pattern of checking if the player is valid avoids crashing if opening the Vickypedia in the Main Menu`）。**如果你在概念文本里用数据函数取对象名，照抄这个模式**。
6. **`is_loading_tip = yes` 会把概念塞进加载界面提示池**（127 个原版概念这么做）。想让自己 mod 的概念出现在加载提示里，加这一行。

### 16.6 实战提示

| 目标 | 做法 | 注意 |
|---|---|---|
| **新增自定义 loc** | 在 `common\customizable_localization\` 新建 `.txt`，写 `<键名> = { type = <scope>  text = { ... } ... }` | **必须**给每一个 `localization_key` 在 `.yml` 里准备对应条目 |
| **调用它** | 在任意 `.yml` 里写 `[<对象>.GetCustom('<键名>')]` | 对象必须与 `type` 匹配 |
| **改原版动态文本** | 覆盖对应的 `.yml` 键（`localization_key` 指向的键） | **通常不需要碰 `common\`** —— 这是最省力的改法 |
| **改原版「选词逻辑」** | 同键名重写整个 `customizable_localization` 块 | 块级替换 |
| **加语言变格** | 用 `parent` + `suffix` 派生 | 见样本 E |

### 18.7 实战提示

1. **`type` 必须与调用点的 scope 匹配**，否则文本取不到（显示为裸键名或空）。实测 16 种合法类型。
2. **不写 `random_valid` 时是「取第一个 trigger 通过的」**，所以**候选顺序即优先级**。想让某个候选优先，把它排在前面。写了 `random_valid = yes` 才是「在通过的里面随机」。
3. **`fallback = yes` 是兜底，不是普通候选**。原版用法：把无 trigger 的候选标记为 fallback，只在前面的条件候选全挂时用它（`99_br_custom_loc.txt`、`99_es_custom_loc.txt` 里共 16 处）。
4. **`log_loc_errors = no` 用于「故意缺键」**：`99_br_custom_loc.txt:18` 注释逐字：`# log_loc_errors = no # can be added to hide errors`。语言变格派生出的键（`CustomLoc_BR_female_OA` 等）不一定全都写了 `.yml` 条目，用这个字段压掉报错。
5. **`|l` 是小写格式化**：`[SCOPE.sCharacter('x').GetCustom('personality_traits_loc')|l]` —— 因为抽出来的词（`direct` / `persistent`）在句首/句中大小写需求不同。
6. **`demonyms_custom_loc.txt` 是「一个键覆盖 300+ 文化」的范式**：它只有 4 个定义（`getPluralDemonym` 等），每个定义里有几百个 `text` 块，每个都是 `cu:<culture> ?= this` + 一个 `PLURAL_DEMONYM_<culture>` 键。做「按文化动态生成称谓」照抄这个结构。
7. **`99_ru_custom_loc.txt` 占全目录 85% 体积（2 MB）** —— 说明**这是个可以堆量大文件的地方**，性能上官方自己就这么用。
8. **`GetCustom` 不能嵌套自身递归**（会导致无限展开）。原版没有这种用法。

#### 21.3.1 「流向」规则（`.md` 开头逐字，最重要）

`modifier_types.md:1-3`：

```text
# the key determines which category the modifier falls into and thereby its flow through the modifier graph
# for example, a modifier definition key that starts with `country_` with an entry in a static modifier applied to a Power Bloc will flow to countries belonging to that Bloc, but no further
# while a modifier definition key that starts with `state_` with an entry in the same static modifier will flow through countries to all states in that country
```

> **这就是 `country_` / `state_` / `building_` 前缀的真正含义**：它决定了修正符在「修正符图」里能流到哪一层。**不是命名习惯，是语义。**

### 21.5 覆盖 vs 新增

| 目标 | 做法 | 注意 |
|---|---|---|
| **新增修正符类型（脚本仍可用）** | 在 mod 的 `common\modifier_type_definitions\` 新建 `.txt`，写 `<新键> = { script_only = yes  decimals=0  color=good  percent=yes  game_data = { ai_value = 0 } }` | **必须**在 `localization\<lang>\modifiers_l_<lang>.yml` 补 ` <新键>:0 "显示文本"` |
| **新增修正符类型（想出现在 UI 选择列表里）** | **不要**写 `script_only` | ⚠️ **未确认**不写 `script_only` 的新键能否被引擎识别为完整功能（多数原版非 `script_only` 的键都是引擎内置的） |
| **改原版修正符显示** | 同键名重写 `decimals` / `color` / `percent` / `prefix` / `suffix` | 块级替换；影响**所有**用它的地方 |
| **改原版修正符文本** | 覆盖 `modifiers_l_english.yml` 里的同键名条目 | **最省力** |
| **加「纯提示」修正符** | 照抄 `07_description_modifier_types.txt` 的写法（`color` + `boolean = yes`，无 `game_data`） | 注释逐字：`These boolean modifiers only exist to generate tooltips and do not have an actual effect in and of themselves` |

### 21.6 实战提示

1. **「新增修正符类型」的四件套（缺一即显示裸键名）**：
   ① `common\modifier_type_definitions\<任意名>.txt` 里的定义
   ② `localization\<lang>\modifiers_l_<lang>.yml` 里的同键名文本
   ③ 使用它的地方（科技 `modifier` / 法律 / 建筑 / 特质 / `add_modifier`）
   ④ 若是 `boolean = yes`，赋值只能是 `yes`
2. **`script_only = yes` 是 mod 新增修正符的关键开关**。原版 66 处使用，全部集中在 8 个文件，且 `12_ip4_script_modifiers.txt` / `13_ep2_script_modifiers.txt` 就是**官方 DLC 用同样方式新增修正符的范例**（12 个 + 3 个），**直接照抄这两个文件的结构最稳**。
3. **`game_data` 通常可以省**（2,364 个定义里 174 个没写 `game_data`）。但既然 2,190 个都写了，说明**写 `ai_value` 是惯例**；`ai_value = 0` 表示「AI 不因这个修正符而改变行为」。
4. **`prefix` / `suffix` 极少用**（6 + 1 处）。它们的值是 **loc 键**（`"MONEY_PREFIX"` / `"per_wealth"`），不是字面字符串。
5. **`percent = yes` 的含义**：`.md` 逐字强调 `i.e. multiply by 100 and append a % sign, the value underneath is not affected`。所以 `_mult = 0.05` 会显示成 `5%`。
6. **`_add` / `_mult` / `_bool` 后缀是约定而非强制**（实测 9 个键用了其它后缀）。但既然 2,350/2,364 都遵守，**新产品请沿用** —— 引擎在很多地方**按后缀推断行为**（未确认具体机制）。
7. **前缀决定流向**（`.md` 开头三行）。想做「影响国家下所有州」的效果，键名必须用 `state_` 前缀；想只影响国家本身，用 `country_`。
8. **`99_todo_sort_into_other_files.txt` 有 47,477 B** —— 官方自己都没分类完。**不需要模仿这种组织方式**。

## 24. 四条最重要的实战结论

1. **改文本 → 改 `.yml`；改逻辑 → 改 `common\`。**
   本范围 29 个目录里，**概念、特质、角色、互动、修正符的显示文本全部是「键名 = `.txt` 里的键」**。想改文字，只需覆盖 `.yml`，风险最低。

2. **新增内容几乎总要「两处同做」：`common\` 定义 + `.yml` 文本。**
   例外只有：`dna_data`（无 loc）、`named_colors`（无 loc）、`power_bloc_*`（无 loc）、`console_command_macros`（无 loc）、`coat_of_arms`（图案无 loc）。
   **忘补 loc 的症状是：显示裸键名（如 `my_new_trait`）或粉红占位图标。**

3. **官方 `.md` 必须交叉验证，本范围内至少 4 份文档与 1.14.2 实况不符：**

   | 文档 | 不符之处 |
   |---|---|
   | `technology\eras\eras.md` | `start_date` / `end_date` / `icon` 三个字段原版 **0 使用** |
   | `trigger_localization\trigger_localization.md` | **整份是 CK3 遗留**：7 个示例触发器名在 V3 **全部不存在**；数据函数名也是 CK3 的 |
   | `modifier_type_definitions\modifier_types.md` | 文档写 `type_set`，实况是 `game_data.tags`（`type_set` 0 使用）；未记载 `script_only` / `difference_sign` / `game_data.tags` |
   | `genes\genes.md` | 自称 `very incomplete`；`decal` 的 `type` / `atlas_pos` / `alpha_curve` 三字段原版 0 使用；实际字段是 `body_part` / `textures` / `blend_modes` / `priority` / `age` |
   | `dna_data\dna_data.md` | `dna = ""` 字段原版 **0 使用**；未记载 `enabled` |
   | `character_traits\character_traits.md` | 未记载 `agitator_modifier` / `affected_naval_mission_types`；示例键 `notorious` 不存在 |
   | `character_roles\character_roles.md` | 未记载 `texture` / `holding_scores`；`should_use_title_in_name` 原版 0 使用 |
   | `character_templates` / `character_interactions` / `game_concepts` / `customizable_localization` / `effect_localization` / `coat_of_arms` / `flag_definitions` / `alert_types` / `messages` 等 | **完全没有 `.md`**，只有文件内注释或什么都没有 |

   **可靠度排名**：文件内逐字注释 > `.txt` 机械提取 > 官方 `.md`。

4. **⚠️ 数数本身也会错：原版文件里「注释含花括号」和「缩进不一致」是两个真实的陷阱。**
   本篇的第一个数字（`flag_definitions` 顶层键 91）就是错的 —— 该文件把整块字段文档注释掉了，注释里的 `{}` 让深度计数漂移，**漏计 342 项**（正确值 433）。
   `ethnicities` 则同时犯了两个错：2 个定义被加了缩进（**漏计**）、7 个基因键掉了缩进（**多计**），简单 grep 得 40、正确值 36。
   **结论：任何「键数 / 字段数」都必须写明口径，并用两种方法交叉核对。** 完整方法与自检脚本见附录 A.0。

## 附录 A：本篇的证据提取命令（可复现）

> 环境：pwsh（PowerShell）。**读 UTF-8 文件必须加 `-Encoding utf8`**，否则中文/特殊字符乱码。

### A.0 ⚠️ 铁律：先剥离注释，再计花括号

**本篇踩过的坑**：原版 `.txt` 里有**把整块字段文档注释掉**的写法（`flag_definitions\00_flag_definitions.txt` 有 21 行这种注释），
注释里的 `{` / `}` 会让「按行计花括号」的深度漂移，**任何基于深度的统计都会出错**。

```powershell
# 正确做法：对每一行先截断 '#' 之后的内容，再用截断后的行计算深度
$code = $line
$h = $line.IndexOf('#')
if($h -ge 0){ $code = $line.Substring(0,$h) }
# 之后：用 $code 判空 / 匹配键名 / 计花括号；用 $line 显示原文
```

**自检方法**：整个文件读完时深度必须回到 0。若不为 0，说明该文件有注释外的不平衡（或字符串里含花括号），此时**不要相信任何基于深度的结果**。

```powershell
# 找出所有「深度不平衡」的文件
Get-ChildItem $dir -Recurse -File -Filter *.txt | ForEach-Object {
  $bal=0; foreach($l in (Get-Content $_.FullName -Encoding utf8)){
    $bal += ([regex]::Matches($l,'\{')).Count - ([regex]::Matches($l,'\}')).Count }
  if($bal -ne 0){ "$($_.Name)  final-depth=$bal" } }
```

### A.4 在指定块内提取字段（如 `flag_definition = { }`、`interest_group_leader_usage = { }`）

```powershell
function InBlock([string]$dir,[string]$block,[int]$rel){
  $out=[ordered]@{}
  Get-ChildItem $dir -Recurse -File -Filter *.txt | ForEach-Object {
    $lvl=-1
    foreach($line in (Get-Content $_.FullName -Encoding utf8)){
      $code=$line; $h=$line.IndexOf('#'); if($h -ge 0){ $code=$line.Substring(0,$h) }   # ★ 必须剥离注释
      $t=$code.Trim(); if($t -eq ''){continue}
      if($lvl -eq -1){ if($t -match "^$block\s*=\s*\{"){ $lvl=1 }; continue }
      if($lvl -eq $rel -and $t -match '^([A-Za-z_][A-Za-z0-9_]*)\s*='){
        if(-not $out.Contains($Matches[1])){$out[$Matches[1]]=0}; $out[$Matches[1]]++ }
      $lvl += ([regex]::Matches($code,'\{')).Count - ([regex]::Matches($code,'\}')).Count
      if($lvl -le 0){ $lvl=-1 } } }
  $out }
InBlock "$g\flag_definitions" "flag_definition" 1
  # → allow_overlord_canton, allow_revolutionary_indicator, coa, coa_with_overlord_canton,
  #   overlord_canton_offset, overlord_canton_scale, priority, subject_canton, trigger
InBlock "$g\character_templates" "commander_usage" 1
  # → chance, country_trigger, earliest_usage_date, latest_usage_date, role
```

> **若字段个数看起来偏少，先怀疑注释未剥离**。对 `flag_definitions` 用不剥离注释的版本会得到 9 个字段（碰巧正确），
> 但用同一脚本处理别的目录就可能漏字段。**统一剥离注释是唯一稳妥做法。**

### A.5 更简单但更脆的替代法：按列 0 直接 grep

```powershell
Select-String -Path "$dir\*.txt" -Pattern '^([A-Za-z_][A-Za-z0-9_]*)\s*=\s*\{' -Encoding utf8
```

**这个方法在缩进规范时与深度法等价，且不受注释干扰**（因为注释行以 `#` 开头，不匹配 `^键名`）。
**但它有两个失败模式**（都在 `ethnicities` 里真实发生了）：

| 失败模式 | 后果 | 实例 |
|---|---|---|
| 定义被加了缩进 | **漏计** | `01_ethnicities_asian.txt:37` 的 `    asian = {` |
| 子键缩进缺失掉到列 0 | **多计** | `01_ethnicities_central_african.txt:64` 的 `gene_chin_forward = {` |

**结论：两个方法都要跑，结果不一致时人工核对差异行。**
