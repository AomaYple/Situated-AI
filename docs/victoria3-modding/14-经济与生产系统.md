## 1. 通用机制：`INJECT:` / `REPLACE:` 家族（**本节适用于全部 13 个目录**）

这是经济系统 mod 开发中**最重要的一条**，也是 `02-Mod结构与加载.md` 未覆盖的**键级**覆盖机制。

### 1.1 六个关键字

| 关键字 | 行为 | 目标不存在时 |
|---|---|---|
| `INJECT:` | 把脚本**追加**到已有条目末尾 | **报错** |
| `REPLACE:` | 用新定义**整体替换**已有条目 | **报错** |
| `TRY_INJECT:` | 同 `INJECT:` | 静默跳过 |
| `TRY_REPLACE:` | 同 `REPLACE:` | 静默跳过 |
| `INJECT_OR_CREATE:` | 同 `INJECT:` | **创建**该条目 |
| `REPLACE_OR_CREATE:` | 同 `REPLACE:` | **创建**该条目 |

### 1.2 处理顺序（决定谁赢）

```text
INJECT_OR_CREATE → REPLACE_OR_CREATE → TRY_INJECT → TRY_REPLACE → INJECT → REPLACE
```

- 只有**同一关键字**之间的冲突才用文件名 ASCII 顺序决定胜负。
- `REPLACE:` 永远赢过 `REPLACE_OR_CREATE:`（无论文件名顺序）。
- `REPLACE:` 会覆盖先前 `INJECT:` 的结果；反之 `REPLACE_OR_CREATE:` 之后的 `INJECT:` 仍能生效。

### 1.3 硬性限制

1. **关键字只能用在文件的顶层块上**。以下写法**非法**（官方文档明确给出反例）：
   ```pdx
   building_example = {
       INJECT:production_method_groups = {
           pmg_foo
       }
   }
   ```
   → 这意味着**无法注入到子块内部**（例如无法只往某个 PM 的 `building_modifiers` 里塞一条）。
2. 大多数 **trigger / effect 块不可重复注入**：若目标已有同名块，`INJECT:` 会失败或被覆盖。
   例外：可多次定义的块（如 `ai_strategy` 的 `wargoal_scores`）会**追加**一个重复块，可能导致「后块覆盖前块中的同名子元素」。
3. `INJECT:` 对 `scripted_effects` / `scripted_triggers` 无效——会退化为 `REPLACE:`。

### 2.5 覆盖 vs 新增

| 做法 | 证据 |
|---|---|
| **改原版建筑 → 用 `INJECT:` / `INJECT_OR_CREATE:`** | 本机 mod 在 `buildings` 目录：`INJECT_OR_CREATE` 46 次、`INJECT` 3 次、`REPLACE` 2 次，**同名键 51 个、全新键 0 个** —— 即**没有任何 mod 新增建筑**，全是改原版 |
| 覆盖文件 | 必须与 `01_industry.txt` 等同名同路径，**整个文件替换** |

**陷阱（本目录特有）**：
1. **`ai_privatization_deisre` 是 `buildings.md` 的拼写错误**。实测文件里该字段根本不存在；真实键名是 **`ai_nationalization_desire`**（12 次，取值分布 `0.5`×4 / `0.25`×4 / `-0.25`×3 / `1.0`×1）。写文档里的名字**不会生效**。
2. **建筑的 PM 绑定字段叫 `production_method_groups`，不是 `production_methods`**。`buildings.md` 第 60 行写的是 `production_methods = { # list of Production Method Groups }`，实测 115/115 个建筑用的都是 `production_method_groups`。
3. **`should_auto_expand` 空内容反噬**（`buildings.md` 第 65 行原文）：
   > *"if this trigger has any contents at all, the game will think the building is potentially auto-expandable, so do not write triggers that can never evaluate to true here"*
4. `ai_value` 作用域是 **state**，且文档警告：*"be careful when using this as applying complex triggers to it may negatively impact performance in a significant way"*（`buildings.md` 第 49–52 行）。

## 3. `building_groups` —— 建筑分组

**路径**：`common\building_groups\00_building_groups.txt`（1 个文件，775 行，69 个组）

### 3.1 用途

建筑分组是一个**树**（`parent_group`），它提供三类东西：
1. **继承链**：子组继承父组的土地类型、现金储备上限、地租规则等；
2. **共享经济属性**：税收、奴隶制、规模经济、基础设施占用、招聘速率、城市化；
3. **AI 参数**：外资比例、自投资概率、规模经济 AI 权重。

> **没有官方 `.md`**，但文件**第 1–25 行**是一张内嵌的字段注释表（`# 字段 = 取值  说明`）。这是本目录的"官方文档"。

### 3.2 文件组织

单文件。所有 69 个组名一律 `bg_` 前缀（实测 69/69）。组名用 `parent_group` 串成树。

## 4. `production_methods` —— 生产方法（PM）

**路径**：`common\production_methods\`（15 个 `.txt` + `production_methods.md`，**436 个 PM**）

### 4.1 用途

PM 是"建筑里可切换的配方"。它决定：
- **投入什么商品、产出什么商品**（通过 `building_modifiers` 里的 `goods_input_*_add` / `goods_output_*_add`）；
- 雇佣结构（`building_employment_*_add`）；
- 对国家 / 州 / 建筑的修正（`country_modifiers` / `state_modifiers` / `building_modifiers`）；
- 解锁条件（科技 / 法律 / 其他 PM / 权力集团原则 / 宗教 / 地理区域 / 公司类别）；
- **AI 倾向**。

> **关键认知**：PM **不直接写** `input = {}` / `output = {}`。投入产出全部通过
> `building_modifiers.workforce_scaled` 下的 `goods_input_<good>_add` / `goods_output_<good>_add` 表达。

### 4.2 文件组织

| 文件 | 内容 |
|---|---|
| `00_dummy.txt` | 只有一个 `pm_dummy`（5 行），用于纯图形建筑 |
| `01_industry.txt` … `14_companies.txt` | 与 `buildings` **同名同序号**，一一对应，便于定位 |
| `production_methods.md` | 官方字段文档 |

**键名规律**：PM 一律 `pm_` 前缀，PMG 一律 `pmg_` 前缀，且 PMG 名通常内嵌所属建筑名
（如 `pmg_base_building_food_industry`）—— 这是**约定**，非引擎强制。

> ⚠️ **提取陷阱（实测踩到）**：PM 键名**允许包含连字符 `-`**。vanilla 中有 3 个：
> `pm_ammonia-soda_process`（`01_industry.txt`）、`pm_coal-fired_plant`、`pm_oil-fired_plant`（均在 `06_urban_center.txt`）。
> 用常见的 `^[A-Za-z_][A-Za-z0-9_]*\s*=` 正则提取会**漏掉这 3 个**，得到 433 而不是正确的 **436**。
> 本文所有键数均以 `^[A-Za-z_][A-Za-z0-9_-]*\s*=` 复算过；其余 13 个目录**无**含连字符的键（已逐目录核验）。
> 另：`06_urban_center.txt` 中有一行被注释掉的 `#pm_hydroelectric_plant = {`，不构成定义。

## 5. `production_method_groups` —— 生产方法组（PMG）

**路径**：`common\production_method_groups\`（15 个 `.txt` + `.md`，197 个 PMG）

### 5.1 用途

PMG 是**互斥 PM 的集合**。同一时刻，一个 PMG 里**有且仅有一个 PM** 处于激活状态
（`production_method_groups.md` 第 2 行原文：*"One and only one must be active at any one time"*）。

建筑的 `production_method_groups = { ... }` 列出它需要几个 PMG 槽位；
每个槽位各自从对应 PMG 的成员里选一个 PM。

### 5.2 文件组织

与 `buildings` / `production_methods` **完全同构**：`00_dummy.txt` + `01_industry.txt` … `14_companies.txt`。
三个目录的序号一一对应，定位某个工厂的机制时按同一序号开三个文件即可。

### 5.3 完整字段列表（**`.md` 与实际 100% 吻合，仅 4 个字段**）

| 字段 | 实测次数 | `.md` | 说明 |
|---|---:|---|---|
| `production_methods` | 197 | ✅ | 成员列表（**裸标识符，无 `=`**） |
| `texture` | 196 | ✅ | 混合配置时显示的图标 |
| `ai_selection` | 60 | ✅ | `most_profitable`（默认）/ `most_productive` |
| `is_hidden_when_unavailable` | 27 | ✅ | 组内 PM 全都不可切换时是否隐藏整组 |

> **注意 `production_methods` 块内部是裸键名列表**，形如 `pm_bakery`（没有 `= { }`），
> 所以用「`键名 = {`」规则做机械提取时会**漏掉**成员，只会得到 4 个字段。这是本目录提取时最容易踩的坑。

## 12. `pop_needs` —— POP 需求

**路径**：`common\pop_needs\00_pop_needs.txt`（1 个文件，**15 个需求类别**，无官方 `.md`，但**文件头 4 行有注释字段表**）

### 12.1 用途

定义 POP 的**需求类别**（如"基础食物"、"麻醉品"、"奢侈品"）。每一类里挂若干**候选商品**，
各自带权重与供给份额上下限。POP 会按市场供给情况在这些商品间**替代消费**。
`buy_packages` 决定每个财富等级在各类别上花多少，`pop_needs` 决定这些钱**买什么**。

### 12.2 文件组织

单文件，15 个顶层键（实测，与 `buy_packages` 引用的 15 个类别**完全一致**）：

```text
popneed_basic_food       popneed_communication   popneed_crude_items
popneed_free_movement    popneed_heating         popneed_household_items
popneed_intoxicants      popneed_leisure         popneed_luxury_drinks
popneed_luxury_food      popneed_luxury_items    popneed_services
popneed_simple_clothing  popneed_standard_clothing popneed_stimulants
```

命名规律：一律 `popneed_` 前缀（15/15）。

### 12.3 完整字段列表

**(A) 类别级字段（深度 1）**

| 字段 | 实测次数 | 来源 | 说明 |
|---|---:|---|---|
| `default` | 15 | 实测（文件头未记录） | 默认商品，如 `default = fabric` |
| `entry` | 52 | 实测（文件头未记录） | 候选商品条目块，**每个类别可重复多次**（15 个类别共 52 个条目） |
| `obsession_demand_min` | 4 | 实测（文件头未记录） | 迷恋时的需求下限倍率 |
| `obsession_demand_mult` | 4 | 实测（文件头未记录） | 迷恋时的需求倍率 |
| `prestige_goods_demand_increase` | 4 | 实测（文件头未记录） | 名贵商品的需求提升 |

> 三个 `obsession_*` / `prestige_goods_*` 字段**只出现在 4 个类别上**（`popneed_intoxicants`、`popneed_stimulants`、`popneed_luxury_items`、`popneed_luxury_drinks` 等 —— 实测 4 组，行号 L181–183、L221–223、L329–331、L377–379）。

**(B) 条目级字段（`entry` 块内部，深度 2）**

文件头第 1–4 行的注释表（**逐字**）：

```pdx
# goods						The good being referenced
# weight					The base weight that is applied to this good based on market Sell Order share
# max_supply_share			The maximum weight that can be applied to this good based on market Sell Order share, relative supply above this amount will have no further impact on base weight
# min_supply_share			If above 0, a minimum of this multiplier of the base weight will be applied to a good regardless of its market Sell Order share
```

| 字段 | 实测次数 | 说明 |
|---|---:|---|
| `goods` | 52 | 引用的商品键（**不带 `g:` 前缀**，裸键名） |
| `weight` | 50 | 基础权重 |
| `max_supply_share` | 50 | 市场卖出订单份额的上限权重 |
| `min_supply_share` | 50 | 下限权重（>0 时生效） |

> `goods` 52 次 > 其余 3 个 50 次 → **有 2 个 `entry` 只写了 `goods`，没写权重字段**（用默认）。

### 12.4 典型语法（逐字引用）

最简单的一类 —— `common\pop_needs\00_pop_needs.txt` 第 6–24 行：

```pdx
popneed_simple_clothing = {
	default = fabric

	entry = {
		goods = fabric

		weight = 1

	}

```

带迷恋/名贵商品参数的完整类 —— 第 178–207 行：

```pdx
popneed_intoxicants = {
	default = liquor

	obsession_demand_min = 0.75
	obsession_demand_mult = 1.75
	prestige_goods_demand_increase = 0.75

	entry = {
		goods = liquor

		max_supply_share = 0.75
```

| 做法 | 证据 |

> 但官方文档同时警告"后块覆盖前块同名子元素"可能产生意外行为 —— **需实测验证，本文标为未确认**。

## 16. 实战配方

### 16.1 改一个原版建筑的 AI 意愿（最小改动）

```pdx
# my_mod/common/buildings/zz_mymod_buildings.txt
INJECT:building_food_industry = {
	ai_nationalization_desire = 0.5
}
```

依据：`ai_nationalization_desire` 实测存在于 `buildings` 深度 1（12 次），
`INJECT:` 在 `buildings` 目录被真实 mod 使用（`3227982912` 的 `kai_buildings.txt:1`）。

### 16.2 改一个原版 PM 的投入产出（**注意不能注入子块**）

```pdx
# my_mod/common/production_methods/zz_mymod_pm.txt
INJECT:pm_craftsman_sewing = {
	building_modifiers = {
		workforce_scaled = {
			goods_output_luxury_clothes_add = 50
		}
	}
}
```

依据：`building_modifiers` → `workforce_scaled` → `goods_output_*_add` 三层结构实测于
`01_industry.txt`（393 / 512 / `goods_output_luxury_clothes_add` 2 次）。
真实 mod 同构写法见 `3647628156` 的 `Ultra_Wo_industry.txt`。

⚠️ 这会**追加第二个 `building_modifiers` 块**。原块的限制仍在，但引擎如何处理重复块
（合并 or 后者覆盖前者）**未确认**。**最保险的做法是 `REPLACE:` 整个 PM 并抄全原定义。**

### 16.3 新增一家公司（**不碰任何原版文件**）

```text
my_mod/
├─ common/company_types/zz_mymod_companies.txt     ← 新增键名，无 INJECT
├─ common/prestige_goods/zz_mymod_prestige.txt     ← 可选
├─ localization/simp_chinese/my_mod_l_simp_chinese.yml
└─ gfx/interface/icons/company_icons/…             ← 图标
```

必备项（据 `99_basic_companies.txt` 第 1–66 行的 66 行模板）：`icon` `background` `category` `flavored_company` `building_types` `extension_building_types`
`possible` **`prosperity_modifier`** **`ai_will_do`**。

> ⚠️ **`ai_will_do` 不写 = AI 永不成立该公司**（`companies.md:51`）。vanilla 221/221 全写。

### 16.4 给所有工厂加一个自建 PM（完整链路）

| 步 | 文件 | 内容 |
|---|---|---|
| 1 | `common/goods/zz_mymod_goods.txt` | （可选）新商品；写 `cost` `category` `texture` |
| 2 | `common/production_methods/zz_mymod_pm.txt` | 新 PM，含 `texture` + `building_modifiers.workforce_scaled.goods_output_*_add` |
| 3 | `common/production_method_groups/zz_mymod_pmg.txt` | 新 PMG，`production_methods = { my_pm }` |
| 4 | `common/buildings/zz_mymod_buildings.txt` | `INJECT:building_x = { production_method_groups = { my_pmg } }` |
| 5 | `localization/simp_chinese/…_l_simp_chinese.yml` | PM 名、PMG 名、（商品名） |
| 6 | `gfx/interface/icons/production_method_icons/…` | PM 图标 `.dds` |
| 7 | `common/pop_needs/zz_mymod_pop_needs.txt` | （若新增商品）`INJECT:popneed_x = { entry = { goods = my_good … } }` |

> 第 3 步说明为什么需要**新** PMG 而不是往原 PMG 里加 PM：
> `production_method_groups` 的 `production_methods` 是**裸列表**，`INJECT:` 会追加一个重复的
> `production_methods` 块（§1.3），行为未确认；而**新建 PMG 再 `INJECT:` 到建筑的
> `production_method_groups`** 同样面临子块注入限制。
> → **结论：给已有建筑换 PMG，目前没有干净的键级做法，只能 `REPLACE:` 整个建筑或覆盖文件。**
