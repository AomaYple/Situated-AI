# 工程原则

本页只定义工程持续约束，每条有稳定编号 `EP-nn`；编号、引用和修订规则及各条的执行方式见[原则索引](README.md)。
环境准备、验证命令、文档维护与 Git 操作步骤见根目录 [CONTRIBUTING.md](../../CONTRIBUTING.md)；Mod 的产品约束见
[Mod 开发原则](Mod开发原则.md)；生成、包结构、证据和恢复的具体合同见[工程交付基线](../design/exec/工程基线-1.0.md)。

## 正确性与变更

- **EP-01 优先级**：正确性第一、速度第二、内存第三。
- **EP-02 优化保持语义**：优化不得改变输入输出、异常行为、回退语义、编码或证据合同；只有在语义等价和所需验证通过后，才接受性能或内存改动。
- **EP-03 显式失败**：对生成器、解析器和校验器采用显式失败：未知字段、作用域、重复定义、非法路径、版本漂移或不完整数据不能被静默忽略。
- **EP-04 缺底本硬失败**：生产生成和打包须读取锁定 Victoria 3 原版；缺少游戏目录或底本漂移时硬失败，不得从冻结产物静默重建。
- **EP-05 删改前核对引用**：删除、移动、改名或合并内容前，检查其调用方、动态注册、测试、CLI、生成入口、文档引用（含链接）及证据用途，并同步维护受影响的内容、链接、忽略规则及测试。

## 游戏版本维护

- **EP-06 单一当前基线**：工程只维护最新正式稳定版游戏的一套有效基线，与 Mod 使用相同的安装身份、原版合同、生成锁和验收输入。
- **EP-07 替换式升级**：升级采用替换基线，不累加多版本支持。
- **EP-08 最新版本核验**：最新版本须有可核验来源，不能把本机已安装版本直接当作远端最新。
- **EP-09 漂移先适配**：发现新版本或底本漂移时先适配、重新生成和验收，不自动放宽版本检查。
- **EP-10 清退旧版本支撑**：移除旧游戏版本专属的适配代码、profile 分派、默认回落、生成与发布分支、重复配置和失效工具。
- **EP-11 共用能力先迁移**：最新版本仍需的共用能力先抽离并按当前底本重新证明，不按文件名或历史来源盲删。
- **EP-12 测试责任迁移**：测试和当前文档随单版本合同更新；删除仅服务旧版本的断言前登记其证明责任，最新版本仍适用的回归、不变量和失败反例迁移保留。清退不得缩减门禁，见 EP-34。
- **EP-13 旧版本不保证可运行**：旧版本不再要求在当前工作树可运行、可生成或可重建。
- **EP-14 历史材料只读**：历史发布标签和原始收据仅作只读追溯；历史材料不作为当前源码或门禁的运行依赖，也不进入当前生产包。
- **EP-15 旧材料移除条件**：旧快照、锁、摘录和重复档案在解除有效引用、履行原字节证据合同后可从当前树移除；Git 历史与已发布标签按 EP-52 保持不变。

## Python、依赖与跨平台

- **EP-16 Python 版本与配置集中**：使用当前基线 Python 版本（见 EP-59 至 EP-61）；项目元数据、依赖与工具配置集中在 `pyproject.toml`。
- **EP-17 环境与库选择**：优先使用仓库 `.venv` 和维护成熟的库。
- **EP-63 优先成熟库**：实现层优先采用维护活跃、社区广泛、有长期支持的成熟库，而非自造同等能力；自造仅在确有性能或正确性收益、或无成熟库可用时采用，并在评审中说明理由。本条与 EP-17（环境与库选择）互补：EP-17 约束运行环境，EP-63 约束实现选型。
- **EP-18 复用既有抽象**：优先复用 Python 标准库及项目已有抽象处理路径、文本、批量盘点、生成和验证。
- **EP-19 不依赖环境假设**：避免 shell 默认行为、用户绝对路径和平台特定假设。
- **EP-20 三平台支持**：工具与测试支持 Windows、macOS、Linux；平台差异显式处理，平台专属依赖通过环境标记声明。
- **EP-21 公共接口**：公共接口提供类型信息和明确错误。
- **EP-22 依赖闭包与锁**：`requirements.lock` 是安装闭包；锁文件变更须说明原因，经 `v3 lock --write` 生成并复核差异。所有依赖和自动化更新均通过审查与 CI。
- **EP-23 检查工具版本固定**：Ruff 与 mypy 的精确版本由 `pyproject.toml` 的 dev 依赖声明，Windows 锁文件记录相同版本，CI 和本地均从该声明安装；升级时独立复核规则、格式与类型检查差异，不让浮动安装无意改变冻结生产源码的检查口径。
- **EP-24 Actions 固定完整 SHA**：GitHub Actions 以完整提交 SHA 固定；更新时沿用同一固定方式。

## Python 版本维护

- **EP-59 Python 单一当前基线**：工程只维护最新正式稳定版 Python 的一套有效基线；当前要求版本由 `pyproject.toml` 的 `requires-python` 字段唯一维护，不在原则页硬编码具体版本号。
- **EP-60 Python 替换式升级**：Python 版本升级采用替换基线，不累加多版本支持；升级时移除旧版本专属的兼容分支、条件导入、类型桩和 classifiers，在当前基线上重新验收后替换。
- **EP-61 优先最新 Python 特性**：在当前基线版本允许的前提下，优先使用最新语言特性、类型系统和标准库 API 替代第三方依赖或旧写法；ruff UP 规则在 CI 中持续拦截已废弃写法。

## 源、生成物与编码

- **EP-25 源与生成物分离**：源码、输入数据与生成物分离；生成物通过唯一生成流程维护，不手改。
- **EP-26 机械内容由生成器维护**：机械表格、统计、指纹和 manifest 由 Python 生成器维护；修改唯一来源后重新生成。
- **EP-27 受控文本编码**：受控文本统一 UTF-8 无 BOM、LF。
- **EP-28 游戏文本 BOM 边界**：Victoria 3 游戏文本仅在安装或打包边界按引擎要求添加 BOM。
- **EP-29 原始字节保留**：原版、第三方和冻结证据保留原始字节。
- **EP-30 生产包内容边界**：标准包只包含 Mod 安装所需内容，不含探针、Python、日志、缓存、本体及第三方资源、历史实验或历史文档；实验不进入默认生产路径或发布包。
- **EP-31 入库边界**：凭据、`.venv`、缓存、日志、临时产物以及 `tools/out/` 中未登记的内容不入库（受控快照与登记证据除外）；可再生的本机输出写入忽略的 `tools/out/`。

## 测试、门禁与证据

- **EP-32 按风险测试**：依据风险使用单元、属性、回归、离线合同和真实底本集成测试。
- **EP-33 规则单源**：生产合同与离线合同共享规则来源，避免复制业务规则。
- **EP-34 门禁不可放宽**：不得删除有效测试、跳过失败、刷新历史证据身份或放宽门禁来宣称全仓通过；也不得借清退旧版本缩减完整测试门、降低覆盖率或资源门限。
- **EP-35 不绕过保护**：CI 失败时定位并修正授权范围内的问题，重新验证后继续标准合并；不能绕过保护。
- **EP-36 证据分类**：区分静态检查、快照、模拟、实测和推断；报告按下表标明证据类别。
- **EP-37 检查的证明范围**：检查通过只证明其明确覆盖的合同，不据此推断未覆盖的运行行为。
- **EP-38 完整资料研究**：工程研究可以在合法访问范围内读取完整安装及相关资料，以建立独立分母和来源闭包；不因材料尚无脚本消费者而漏记，完整资料分母不以脚本当前可读范围裁剪。
- **EP-39 可读取不等于可分发**：可读取不代表可公开分发；本体及第三方资源不进入生产包（EP-30）。
- **EP-40 覆盖声明**：覆盖声明须有独立分母和逐项处置。
- **EP-41 五段分别证明**：原始字节可读取、语法可解析、语义已理解、合法运行时可观察与生产已接线分别证明、分别登记。
- **EP-42 资料不自动成为决策输入**：开发者掌握的资料（读到的文件、定义、历史或二进制线索）不能自动成为国家决策输入，也不自动赋予国家观测权。
- **EP-43 缺口如实登记**：访问或解析失败不得静默排除，也不能冒充引擎不支持；解析器或接线缺口须如实登记。
- **EP-62 完整游戏信息读取**：工具链应尽可能读取、分类和解释锁定安装中所有与 Mod 开发相关的游戏数据（触发器、效果、作用域、策略消费者、科技、地图、政治等类别），以建立完整独立分母，支撑后续 Mod 功能开发；尚未覆盖的读取缺口按 EP-43 如实登记，不静默省略。
- **EP-44 性能结论同口径**：性能结论必须基于可重复、同口径的测量；不同测试身份、并行度或数据不能直接比较。
- **EP-45 性能测量口径**：性能测量固定输入与环境，并报告足以复核的时间及内存口径。

EP-36 的五类证据与报告、PR 中使用的标识符一一对应：

| 证据类别 | 标识符 |
|---|---|
| 静态检查 | `static_check` |
| 快照 | `snapshot` |
| 模拟 | `simulation` |
| 实测 | `runtime` |
| 推断 | `inference` |

表中“实测”指引擎运行期取得的证据，不含读取游戏文件的静态核对。各类证据的证明范围见
[工程交付基线](../design/exec/工程基线-1.0.md)的“证据口径”。E、M、R、U 验收门由
[1.15架构设计](../design/1.15架构设计.md)定义，各自规定要证明什么、不能代替什么；本页不另定门与证据类别的对应规则。

## 发布与恢复

- **EP-46 明确授权**：自动化使用明确授权的版本、渠道和目标身份。
- **EP-47 渠道分别验证**：标签、附件、安装与创意工坊分别验证，部分成功不能签署全流程完成。
- **EP-48 认证不可用即阻塞**：认证不可用须明确阻塞，不以模拟或进程退出码代替真实渠道结果。
- **EP-49 外部操作可恢复**：外部操作可重入、可核对并保留恢复证据。
- **EP-50 重试先核对**：响应丢失先核对实际状态；重试不得移动已发布标签、产生重复工坊条目或覆盖用户后续修改。
- **EP-51 不声称跨服务原子回滚**：跨服务部分失败按阶段处理，不声称跨服务原子回滚。
- **EP-52 主线与标签不可改写**：禁止强制推送 `main`；Git 历史及已发布标签不改写、不移动。

## 文档、来源与验收边界

- **EP-53 文档单一职责**：规则、流程、设计、计划、状态、结果、知识库与生成文档各有单一职责。
- **EP-54 导航页不复制规则**：导航页链接权威来源，不复制第二份规则。
- **EP-55 易变事实标明来源**：散文中的易变事实标明来源或链接到权威收据。
- **EP-56 治理与产品分别验收**：工程治理与产品开发分别验收；纯工程治理以规则、代码、文档、结构与工具的统一和行为保持为范围，不自动恢复产品计划。
- **EP-57 保留真实状态**：保留未完成能力和有效失败的真实状态。
- **EP-58 提交边界**：提交边界与任务边界一致；不把未完成产品候选夹带进入独立治理交付。
