## 二、闸门与基准进 CI（现状矩阵，逐条写清"在哪跑、为什么"）

Windows 跑依赖锁）。

| 检查 | CI | 本机 | 为什么 |
|---|---|---|---|
| `ruff check` / `ruff format --check` / `mypy` | ✅ | ✅ | 不需要游戏 |
| `pytest -m "not integration"` | ✅ | ✅（全量） | 无游戏时 conftest 自动 skip 集成用例 |

| `v3 modgen --check`（68 产物） | ✅ | ✅ | 只比对数据源与盘上产物 |
| `v3 modguard --offline` | ✅ | ✅（在线版） | ①② 的原版真值走快照 |
| `v3 ai-surface --check --offline` | ✅ | ✅ | 同上，且复用同一个 `render()` |

## 三、维护预算（一次改动的固定成本，实测口径）

| 动作 | 实测耗时 | 说明 |
|---|---|---|
| `pytest -q -n auto`（当时 1434 条，全量） | **≈3.5 分钟** | 本机 16 核；这是每次改动的下限成本 |
| `v3 modgen` + `--check` + `modguard` | ≈40 秒 | 生成 + 五道闸门 |
| `v3 verify` + `tables` | ≈1.5 分钟 | 234 条断言 + 172 张表 |
| `v3 citations` | ≈10 秒 | 949 条引用（含一次原版目录索引） |
| **一次完整门禁** | **≈6 分钟** | 上面四项之和 |
| 一次游戏会话（起→观察→5 档→空格→切后台→收尾） | **≈4–5 分钟** | 加载 ≈3 分钟 + 会话 ≈1.5 分钟（`性能仪表侦察.md` 的实测口径） |
| 一次 A/B 对照（12 个月 × 2 局，`perf_compare.py`） | **≈22 分钟** | 每局 ≈11 分钟；`--repeat 3` 约 1 小时 |

**预算口径**：改一个档案的常规成本 = **6 分钟门禁**；要动世界状态的改动 **+ 一次游戏会话**；
要声称性能没退化的改动 **+ 一次 A/B**。这三档写在这里，是为了让"要不要跑"这件事
有依据，而不是凭感觉。

## 四·补、基准进 CI 的口径（阶段 4 出口判据的最后一件）

`01-大方向.md` 阶段 4 的出口判据写着「闸门**与基准**进 CI」。闸门早就在了，基准一直没进 ——
原因写在 `ci.yml` 里：绝对墙钟在共享 runner 上抖动极大（同一次提交能差一倍），当门禁必然误报。
2026-09-24 补上时的取舍是**分开两条**：

| 在哪 | 是什么 | 断言吗 |
|---|---|---|
| CI 的 `bench` job | 不需要游戏的合成样本基准（`SMALL`/`MEDIUM`/`TRICKY`），数字进 job summary + artifact | **不断言**（只留可比口径） |
| 本机普通套件 | `test_cache.py` / `test_audit_leftovers.py` 的「并发下每个文件只解析一次」（**不依赖墙钟**） | ✅ 断言（所以它在并行套件里就能守） |
| 本机基准用例 | `test_audit_leftovers.py` 的解析吞吐下限 | ✅ 断言（要 `-n0`，见 pyproject） |

⇒ 「基准进 CI」的实质收益是**每次 push 都留一份同口径数字**（`tools/ci/bench_summary.py` 汇总），
而真正会红的性能回归由**不依赖墙钟的不变量**在本机守住 —— 这不是打折，是把判据放在它测得住的地方。

## 五、下一次官方更新怎么做（照抄，别再想）

```text
① v3 refresh                      → 表重算 + 正文按归属标记改写
② v3 verify --fix-claims          → 把实测值写回 CLAIMS（非整数的指纹手工改）
③ v3 verify                       → 应回到 234/234；文档漂移应为 0
④ v3 ai-surface --write           → 原版 AI 面变了就重写对照面
⑤ v3 mirror write --sync          → 官方 .md 清单（篇数会变）
  v3 snapshot create --compact    → 刷新入库快照（否则离线通道会红）
⑥ v3 analyze                      → 产物重算（check-outputs 与黄金回归都读它）
  pytest tests/test_golden.py --force-regen + 全量套件
⑦ python -m pdx.game_auto run     → 引擎侧实证
⑧ 机器看守的文档数字：`v3 tables --write` 之外还有几处**手写但被测试看守**的
  （doc 03/07/16/17 的字节数与总览表、README 的用例数/字符总量）——
  跑全量套件就会逐个报出来
```

> ⚠️ **刷快照放在最后一步（顺序不能颠倒）**：上面 ⑤ 里的 `v3 snapshot create --compact`
> 必须在 ①–⑥⑧ 的文档 / 数据源改动**全部落定之后**再跑，且跑完 `git add` 入库；
> `v3 tables --offline` 报的「跑 `--write` 可按快照恢复」**不要照做**（那是把文档倒回快照，
> 不是更新快照）。完整口径见 §四 第 1 条下的「刷快照的处置顺序」。

> ⚠️ **编辑被大量引用的文件会让引用行号漂移**：`v3 citations` 现在会先按行指纹
> 把漂移的那些**找回新行号**（`citations.relocate`）再报其它问题 —— 不然那句
> 「第 N 行的内容变了（原版更新？）」会把人引去看官方更新，而真相是自己刚编辑过那个文件。
> 数据源里的引用改完记得接 `v3 modgen --write`，最后 `v3 snapshot create --compact`。

> ⚠️ **`v3 snapshot diff` 的口径陷阱**：入库的快照是**某一轮的域集合**。
> 拿它比新版时差异里会混着**格式变化**（1.14.3 那份 6 个域、1.14.4 是 14 个），
> 命令现在会显式点明「域集合不同」并列出可比的那几个域 —— 别把百万级"删除"当成原版变化。
