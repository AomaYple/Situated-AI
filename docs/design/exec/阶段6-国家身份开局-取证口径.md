## 1. 目标状态（一句话定义"做完"）

> **在不是观察者的一局里**，以**真玩家国家 RUS** 开局；开局前那屏的**规则窗**里能读到
> `rule_sitai_difficulty` 的三档、能改、点「应用」后生效；中英两种界面语言各读到一次；
> 进游戏后日志面板上能读到三行；跑完用户环境原样。

四个"必须"都是判据，缺一个就是没做完：

* **真玩家国家** —— `ZZPROBE AB;PLAYER` 能自报（观察者局 0 行【实测】`自动化范式.md:386-388`）；
* **RUS** —— `je_sitai_ru_reform_window` 的 `is_shown_when_inactive` 是 `c:RUS ?= this`，
  别的国家根本看不见那个 JE（`mod/common/journal_entries/sitai_ru_defeat_window.txt:19-21`）；
* **规则窗** —— 三档能在窗里逐档读到、能改（§3）；
* **双语** —— 中英各读到一次（§4）。

为什么必须 RUS、不能用别国凑：G3 三行挂在**那份档案的 JE** 上，而 JE 的开窗条件是
`c:RUS ?= this` + `has_variable = sitai_ru_defeat_memory` + `legitimacy <= 75`。
国家级的路只有一条：**选 RUS 开局**。

## 6. 环境安全纪律（三条，全部可复算）

1. **改用户配置之前不许有会抛的操作**（backlog **B79**，`docs/design/backlog.md:168`；
   教训原话见 `接续说明.md:177`）。落地顺序（先例：`stage3_rerun.py:626-658`）：

   → **`deploy()`**（第一次动 `content_load.json`）→ 跑 → `finally` 收尾。
   `finally` 只在 try 开始之后才管用 —— 崩在它之前，用户的 23 条 Workshop 配置就留在"只剩 1 条"。
2. **崩了要能自愈**：`preflight.probe_state_backup()` 非空 + 备份在 ⇒ 拿备份还原再继续
   （探针态只可能是我们造成的：用户不会把 `zz_probe*` 加进自己的列表；`preflight.py:298-312`）。
   判据不是"有没有留下痕迹"，而是**当前启用列表本身**（`check_user_config` 第 2 条，`:219-225`）。
3. **跑完必须还原**（三件都算）：
   * `_process_pids()` == `[]`（0 个 `victoria3`；`kill_game()`，`game_auto.py:1479-1495`）；
   * `content_load.json` 的 **sha256 == 跑前**（不是"条数差不多"）；
   * **没有新增备份文件**（`.v3probe-backup` / `.sitai-backup`，`preflight.py:283`）。
     本机现在**已经有一份**遗留 `content_load.json.sitai-backup`（2166 B，2026-09-24 那次事故那一族）：
     本文的口径是**不清它、只报告**（`check_user_config` 对这一条只给 INFO，`:267-276`）——
     删不删是用户的决定，不是脚本的。
   * 前台还给启动前的窗口（`previous`）+ 窗口不缩不炸（先例：`stage3_rerun.py:687-694`）。

**P13 原文**（`01-大方向.md:78`）：*失败要出声：版本不符、引用缺失、闸门不过时必须报错，不许静默降级。*

## 8. 与现有观察者局路径的关系：**独立驱动脚本 + `game_auto` 新增原语**

**结论**：**不新增端到端模式**，**新增一个独立驱动脚本**（建议 `tools/probe/stage6_ui_rerun.py`，
命名沿用 `stage3_rerun` / `perf_compare` / `flow_with_cleanup`），
`game_auto` 里只加**原语**。三条理由：

1. **`start_session()` 是"一条路、失败即抛"的观察者闭环**（`game_auto.py:2418-2452`：用户口径把点火
   定成唯一一条路，回落链已删）。塞第二种流程进去，等于让一条闭环变成两条状态机，
   而两条路的**判据、ROI、语言、前置条件全都不同**（观察者局不需要规则窗，这条需要）。
2. **`game_auto` 至今不碰用户配置**（它只启动/杀进程、点窗口、读日志）—— 这个性质值钱：
   改 `content_load.json` 的纪律收在驱动脚本里（`stage3_rerun.py:626-694` 是既有先例），
   `v3` 子命令只**报告**（`v3 preflight` 的定位，`tools/README.md:116`）。把"改环境"编进
   `game_auto` 的 CLI 会破坏这条分层。
3. **要加的确实是原语，不是流程**：规则卡片的定位、卡片框内的相对点击、规则窗滚动，
   都是"窗口级 UI 原语"，与观察者局共用同一套 ROI/偏移/尺度机制（`:1130-1151` 那个 bug 的教训）。
   放进 `game_auto` 才能被 `test_game_auto.py` 的**假窗口**用例看守（那套用例不开游戏）。

**要加的原语**（各有出处，不是拍脑袋）：

| 原语 | 为什么需要 | 现有缺口的出处 |
|---|---|---|
| `mouse_wheel(hwnd, x, y, clicks)` | 规则列表一屏放不下 16 条（`game_rules.gui:105-115`） | `game_auto` 里**没有**滚轮：只有 `click_client` / `press_key` / `press_chord` / `type_text`（`:1256/598/609/651`）。`pydirectinput.scroll` 与已用的 `moveTo/click` 同源 |
| `find_in_roi(..., directory=…)` 或 `locate(..., directory=…)` 贯通 | 中英两套模板要分目录；`locate/load_template` 已支持 `directory=`，`find_in_roi` 还没有（`:1153-1175`） | `:1153-1175` 没有 `directory` 形参 |
| `wait_until_text_stable`（帧比对） | "档名跟着换"要等引擎画完一帧；直接连点会落空（既有 `STEP_SETTLE = 0.35`，`:165`） | 现有 `wait_until`（`:524-568`）够用，**用不用新增由实现定**，但"等画面稳定"这条判据必须有 |
