## 1. 结论（一句话）

**仓库侧 `.py/.md/.toml/.json/.yml/.txt` 等一切文本文件必须 UTF-8 无 BOM + LF，
唯一例外是引擎会去读的游戏侧文本：`mod/**` 与 `tools/probe/**` 下的 `.txt` / `.yml` 必须带 BOM。**

实况：受控文件 **369** = 文本 **366** + 二进制 **3**；
清单①（必须带 BOM）**117** 条，全部带 BOM，缺 0；
清单②（必须不带 BOM）**252** 条，误带 0；CRLF **0** 处。
⇒ **当前实况两清单各 0 违规**（`v3 modgen --check` 与 5 条既有 BOM 用例也各自绿）。

## 2. 判定规则（纯 Python，字节级，不依赖 PowerShell）

| 项 | 判据（`bytes` 层面） | 反例长什么样 |
|---|---|---|
| 带 BOM | `data[:3] == b"\xef\xbb\xbf"` 即 `(239, 187, 191)` | 前三字节不是它 ⇒ **无 BOM** |
| 有 CRLF | `b"\r\n" in data` ⇒ **不是 LF-only** | 只要出现一处 `0D 0A` 即违规 |
| 二进制 | 前 **8000** 字节里含 NUL（`b"\x00"`）⇒ 跳过，不做上面两条判定 | 与 git 自己的文本判法同源：三个 PNG 的 NUL 出现在**第 8 字节**（`89504e470d0a1a0a` 之后） |

三条实现纪律（踩过才知道）：

1. **不许用 `encoding="utf-8-sig"` 判断有没有 BOM** —— 那个编码名会把 BOM 悄悄吃掉，
   于是"带 BOM 的 `.py`"在 Python 眼里永远干净。判 BOM 只能看**原始字节**。
2. **不许用 `Path.read_text()` 判 LF** —— Windows 上文本模式会把 `\r\n` 归一成 `\n`，
   CRLF 在字符串里永远看不见（`收口清单.md` C.0 记的正是这类假绿）。
3. **不许用 PowerShell 往返判定** —— `Get-Content` / `Set-Content` 会按 GBK 解码再按 UTF-8 写，
   实测把中文变成双重编码并**写进 BOM**（`239,187,191`，`接续说明.md` §6 有完整现场）。

**行数怎么数（本文口径，全仓文档一致沿用）**

* **判据：行数 = LF 计数** = `data.count(b"\n")`。因为本仓受控文本**强制末尾 LF**，它同时等于
  物理行数与 `text.splitlines()` 计数；三者不等**只可能**是缺末尾 LF —— 那本身是卫生问题，
  按上面第 2 条修文件，**不许反过来改数字**。
* **复算命令**（文档里任何「N 行」都按这一条读与核）：
  `.venv\Scripts\python.exe -c "import pathlib;p=pathlib.Path('…');print(p.read_bytes().count(b'\n'))"`
* **为什么写死**（`t66` 现场）：文档里到处把「N 行」当**证据读数**用，而先前有人按「换行数 + 1」
  数，把 `docs/reports/目标函数表口径-独立复核.md` 写成 **252**（实测 **251**）—— 复核者按 251
  复算就对不上。⇒ 报「N B / M 行」时两个数都按**字节级现读**（`stat().st_size` / `count(b"\n")`），
  与上面 BOM/LF 两条判据同一口径；**`t66` 已按它做了全量对账**（清单与残项见 `backlog.md` B102）。

## 4. 两张清单

### 清单① 必须带 BOM：117 条（`mod/**` 与 `tools/probe/**` 下的 `.txt` / `.yml`）

| 路径 | 条数 | 后缀构成 |
|---|---:|---|
| `mod/localization/{english,simp_chinese}/sitai_*.yml` | 18 | `.yml` ×18 |
| `mod/common/{defines,game_rules,journal_entries,scripted_effects,static_modifiers}/sitai_*.txt` | 39 | `.txt` ×39 |
| `tools/probe/zz_probe_{a,b,ab,h1,risky}/**` 的 `.txt` / `.yml` | 60 | `.txt` ×42 · `.yml` ×10 · `tools/scripted_tests/*.txt` ×5 |
| **合计** | **117** | `.txt` ×89 · `.yml` ×28 |

**口径写成路径式，不写成后缀式**：

```text
必须带 BOM  ⇔  路径以 mod/ 或 tools/probe/ 开头  且  后缀 ∈ {.txt, .yml}
```

理由（这是本次盘点最容易踩的坑）：**全仓只有两个 `.yml` 不在 `mod/` 或 `tools/probe/` 下**，
它们**必须不带 BOM**：

```text
.github/workflows/ci.yml                       GitHub Actions（YAML 解析器）
tests/test_golden/test_artifact_digests.yml   黄金回归指纹（pytest-regressions 读）
```

任何"`.yml` 一律带 BOM"的规则都会**当场判错这两条**；反之"`.yml` 一律不带 BOM"会
放倒 28 条游戏侧本地化。所以判据的主键必须是**路径**，后缀只是次级条件。

### 清单② 必须不带 BOM：252 条（其余全部受控文件）

| 类别 | 条数 | 依据 |
|---|---:|---|
| `.py` | 152 | `收口清单.md:70`「仓库 `.py` 一律 UTF-8 **不带 BOM**、LF」；BOM 会让 `ast.parse` 直接 `SyntaxError`（同文件 C.0 记的实测事故） |
| `.md` | 70 | 人读文档；`modgen._writes_bom` 明确 `.md` 不带 |
| `.txt` / `.yml`（**不在** `mod/`、`tools/probe/` 下） | 2 | 上面那两个 CI / 黄金回归文件 |

## 5. 引擎侧必须带 BOM 的依据

**引擎行为（两条，都有日志原文）**

| 文件类型 | 引擎行为 | 日志原文 / 位置 |
|---|---|---|

| `docs/design/exec/阶段3-结果.md:34` | modgen 产出：「游戏侧带 BOM，两次生成逐字节一致」 |

| 既有测试（钉在用例里） | `tests/test_experiments.py:92-101`（`PROBE_DIR` 下全部 `.txt`/`.yml` 必须 BOM）、`tests/test_h1_probe.py:228`（生成物必须 BOM）、`tests/test_modgen.py:512-524`（**游戏侧带、文档不带**）、`tests/test_ab_probe.py:474` |
| 盘面自证 | `v3 modgen --check` → `modgen.check()`（`modgen.py:1834-1850`）对盘上产物报「缺 UTF-8 BOM」，即**产物侧**的 BOM 有机械判据 |

**据此定三级口径，并把我们的执行口径收在最严那一级：**

| 级别 | 对象 | 引擎是否强制 | 本仓库口径 |
|---|---|---|---|
| 硬要求 | `localization/**/*.yml` | 是（缺 BOM 报错退出） | **必须带** |
| 建议 | 其它 `.txt` 脚本 | 否（`lexer.cpp:285` 提醒后继续） | **仍然必须带**：0 成本、少 10+ 条日志噪声、且真出问题时不至于把 loc 的硬报错淹掉 |
| 不适用 | `.md` / `.json` / `.toml` / `.py` | — | **必须不带** |

> **一句话修正一处措辞**：仓库里多处（如 `modgen.py:25`）写的是「缺 BOM 的表现是*文件像没生效*」。
> 严格说，实测记录到的是「**只有 error.log 里几行提醒、控制台不出声**」，不是零证据静默；
> loc 那条则是硬报错。本审计以日志原文为准，避免把"提醒被忽略"当成"引擎没说话"。

## 6. 当前实况数字与复算命令

### 实况（2026 现场，`git ls-files` 369 条）

```text
受控文件 369 = 文本 366 + 二进制 3
清单①（必须带 BOM）117 条 · 其中带 BOM 117 · 缺 BOM 0
清单②（必须不带 BOM）252 条 · 其中误带 BOM 0
CRLF 违规 0
判定 = 干净
```

### 复算

**命令 1（首选：完整判据，纯 Python，退出码即结论）** —— 口径与本文 §2 一字不差：

```powershell
# 把下面这一段落存成 UTF-8 无 BOM 的 .py（或直接用 §9 扩展后的用例），在仓库根执行
.venv\Scripts\python.exe - <本文 §2 判据>       # 见 t2 证据脚本；退出码 0 = 干净，1 = 有违规
```

**命令 1 的脚本文本**（拷进 `%TEMP%\t2-criteria.py` 后跑 `python %TEMP%\t2-criteria.py <仓库根>`；
本次实跑用的就是这一份，输出即上面那段。之所以不做成一行 `-c`：PowerShell 传参会把
Python 单行里的双引号吃掉（实测过），而且下面这段本身就是"判据的规范文本"）：

```python
"""文件编码判据：受控文件盘点 + 两张 BOM 清单 + CRLF。退出码 0 干净 / 1 有违规。"""

import subprocess, sys
from pathlib import Path

BOM, NUL, CRLF, ZERO = bytes((239, 187, 191)), bytes((0,)), bytes((13, 10)), bytes((0,))

root = Path(sys.argv[1]).resolve()
out = subprocess.run(
    ["git", "-c", "core.quotepath=false", "ls-files", "-z"],
    cwd=root,
    capture_output=True,
    check=True,
).stdout
tracked = [p.decode("utf-8") for p in out.split(ZERO) if p]

text, binary, bom, crlf = [], [], [], []
for rel in tracked:
    data = (root / rel).read_bytes()
    if NUL in data[:8000]:  # 二进制：跳过 BOM/LF 判定（必须放在最前）
        binary.append(rel)
        continue
    text.append(rel)
    if data[:3] == BOM:
        bom.append(rel)
    if CRLF in data:
        crlf.append(rel)

controlled = [
    r
    for r in text
    if r.endswith((".txt", ".yml")) and (r.startswith("mod/") or r.startswith("tools/probe/"))
]
missing, stray = [r for r in controlled if r not in bom], [r for r in bom if r not in controlled]

print(f"受控文件 {len(tracked)} = 文本 {len(text)} + 二进制 {len(binary)}")
print(
    f"清单①（必须带 BOM）{len(controlled)} 条 · 带 BOM {len(controlled) - len(missing)} · 缺 {len(missing)}"
)
print(f"清单②（必须不带 BOM）{len(tracked) - len(controlled)} 条 · 误带 {len(stray)}")
print(f"CRLF 违规 {len(crlf)}")
for tag, rows in (("缺 BOM", missing), ("多 BOM", stray), ("CRLF", crlf)):
    for r in rows:
        print(f"  {tag}: {r}")
bad = bool(missing or stray or crlf)
print("判定 =", "有违规" if bad else "干净")
sys.exit(1 if bad else 0)
```

> 沙箱/副本场景要额外 `set PYTHONPATH=<副本>\tools`：仓库的 `.venv` 是 editable 安装，
> `site-packages/__editable__.*.pth` 把**真仓库**的 `tools` 塞在了 `sys.path` 里，
> 不覆盖的话 `pdx.config.REPO` 会指回真仓库 —— 这个坑实测踩到过，见 §7。

## 7. 负对照（判据真的抓得住，不是"恰好干净"）

在**临时沙箱**里做（不碰真仓库任何文件）：沙箱 = 临时目录下一个最小仓库骨架
（`pyproject.toml` + `.gitattributes` + `src/pdx` + `tests` + `docs` + `research` 清单
+ **git 受控的** `mod/**` 与 `tools/probe/**`），`git init` 后自成受控集合，
`pdx.config.REPO` 靠 `__file__` 指向沙箱根 —— 于是 `config.REPO == <沙箱>`。

| # | 注入的违规 | 判据（§2） | 既有用例 `test_repo_hygiene.py` |
|---|---|---|---|
| ① | 无（干净沙箱） | `exit 0`，**干净** | `6 passed`，`exit 0` |
| ② | `docs/design/exec/接续说明.md` 全文件转 CRLF（237 处） | `exit 1`，点名该文件 | **1 failed**，`exit 1`，报「第 2 行（共 237 处）」 |
| ③ | `src/pdx/injected.py` **加** BOM（仓库侧违规） | `exit 1`，`多 BOM: src/pdx/injected.py` | —— |
| ④ | `mod/common/static_modifiers/sitai_injected.txt` **去** BOM（引擎侧违规） | `exit 1`，`缺 BOM: mod/…/sitai_injected.txt` | **6 passed（全绿）** ← 见下 |

**④ 就是缺口本身，实测复现过**：把一处 BOM 加进 `src/pdx/`、把一处 BOM 从 `mod/` 拿掉，
当前套件**依然 6 passed**。原因是现有 `_candidates()`（`test_repo_hygiene.py:34-41`）的
根只有 `src/pdx`、`tests`、`docs`、`research` + 3 个零散文件，
后缀只有 `.py/.md/.toml/.yml/.yaml/.json`；实测该 scope 命中 **200** 条
（含 `mod/` **0** 条、含 `tools/probe/` **0** 条，后缀集合 `['json','md','py','toml','yml']`，
连 `.txt` 都不在内）。而唯一全仓扫 `.txt`/`.yml` 的 BOM 用例在 `test_experiments.py`，
它只覆盖 `PROBE_DIR`（`tools/probe/`），**不覆盖 `mod/`**。

一条顺带确认的机器事实：沙箱里跑 pytest，`config.REPO` 确实等于沙箱根（`_candidates()` 200 条
落在沙箱内），所以"负对照用沙箱"这件事成立 —— 前提是 `PYTHONPATH` 覆盖掉 editable 的 `.pth`。

## 8. 边界（这些不算违规）

| 情形 | 处理 | 理由 |
|---|---|---|
| 二进制文件（PNG / `*.dds` / `*.xlsx` …） | 跳过 BOM 与 LF 判定 | 前 8000 字节含 NUL；`.gitattributes` 已按 `binary` 钉死 |
| `.gitignore` 忽略的目录（`tools/out/`、`research/official-docs/`、`tools/probe/zz_console_probe/`） | **不在受控集合内** | 口径来自 `git ls-files`；它们是本机产物/逐字镜像。⚠️ 实测 `tools/probe/zz_console_probe/ticktask_timings.csv`（573,732 B）**带 BOM**——它是引擎写出的数据产物、整目录被忽略，所以**不是违规**，但"按目录树扫描"的判据会把它算进去（这正是判据必须锚在 `git ls-files` 上的原因） |
| 未跟踪文件（现场：`tools/probe/mem_baseline.py`、`docs/design/exec/阶段5-9国目标函数表.md`、`tools/tools/`） | 不在受控集合内 | 提交前不判定；提交后自动进入下一次判定 |
| 原版游戏文件、用户 mod 目录 | 永不在本仓库口径内 | 它们由引擎/用户负责，仓库只读写、不改 |

## 9. 机器判据落在哪里：`tests/test_repo_hygiene.py` 的扩展范围

**扩展的目标**：现有那 6 条（CRLF + 元测试）**保留不动**（它们已经绿、覆盖 `docs`/`research` 与
未跟踪文件），新增三条把两颗"引擎侧/仓库侧"的 BOM 钉子钉上。

| 新增用例 | 覆盖后缀 | 判定 | 为什么这么定 |
|---|---|---|---|
| `test_受控文件必须带_BOM` | `mod/**`、`tools/probe/**` 下的 `.txt`、`.yml` | 每条 `data[:3] == EF BB BF` | 清单① ，**只按路径 + 后缀**，不做全仓后缀规则 |
| `test_仓库侧文件不许带_BOM` | 其余全部受控文本文件（`.py/.md/.toml/.json/.yaml/.lock/无后缀` 等） | `not data.startswith(BOM)` | 清单②；一条规则覆盖 `收口清单.md` C.0 的 `.py` 纪律与 `.json` 的启动器口径 |
| `test_受控清单非空`（元测试） | — | `len(受控) >= 117` 且 `len(文本) >= 360` | 防"目录改名/口径写错 ⇒ 扫 0 个文件、永远绿"。照现有 `test_检查范围不为空`（`>20`）的做法，数字按现场实测钉 |

**候选文件怎么来**：`git ls-files -z`（`subprocess` + `-z` 避免中文/空格路径被转义，
实测全仓 `core.quotepath=false` 下 369 条无一条需要引号）。**不用 `rglob`**：`rglob` 会带上
未跟踪文件（实测现有 scope 的 `rglob` 命中 295 条，其中 95 条是 `research/official-docs/`
镜像里的 `.md`），把判据的噪声抬高；`git ls-files` 让"受控"与"提交"严格同义。

**二进制处理**：`if b"\x00" in data[:8000]: continue`。**必须放在 BOM/LF 判定之前**，
否则 PNG 会被当成"缺 BOM"报出来。

**成本量级（实测，Windows 本机、热缓存）**：

| 口径 | 文件数 | 中位耗时 |
|---|---:|---:|
| 全受控 369（现口径 `git ls-files` + 读字节 + 两条判定） | 369 | **0.042 s**（文本 366 个共 **17.71 MiB**，其中两份入库快照 `tools/out/snapshots/*.compact.json` 占 12.14 MiB；扣掉后只有 5.56 MiB） |
| 现有 scope（`rglob` 4 根 + 后缀过滤） | 295 | 0.041 s |
| `test_repo_hygiene.py` 整个模块（pytest 启动 + 6 条） | — | **0.25 s**（`-n0`，实测 `6 passed in 0.25s`） |
| 加上"全受控 369 条"的 BOM 判定后预估 | 369 | `+0.05 s` 以内（读字节是大头，判定是纯切片比较） |

⇒ **秒级以内、无 I/O 放大**：一次全树 `read_bytes()` 是 17.71 MiB（文本 366 个；扣掉两份入库快照
只剩 5.56 MiB），判定本身是纯切片比较；不读游戏、不写盘，`-n auto` 下与现有 `docs` 用例同一量级。

**口径与既有用例的关系**：新判据**不替代** `test_experiments.py::test_探针文件必须带BOM`
（那条是"探针目录内全扫"的更强版本）与 `test_modgen.py::test_游戏侧文件带BOM而文档不带`
（那条钉的是**生成器**的写盘编码）。四条各守一段：生成器写盘 / 探针目录 / 仓库受控全集 / 产物盘面。
