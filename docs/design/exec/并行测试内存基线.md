## 1. 一句话结论

* **测量命令（一条）**：

  ```powershell
  .venv\Scripts\python.exe tools/probe/mem_baseline.py run
  ```

  它同时报出**整套峰值**、**每 worker 峰值**、**总耗时**，产物落 `tools/out/mem/`（机器可读）。
* **当前基线**（本机 i7-11800H / 8 核 16 线程 / 15.80 GiB / Windows 11 / Python 3.14.7）：

  | 组 | 整套峰值 | 每 worker 峰值 | 总耗时 | 状态 |
  |---|---|---|---|---|
  | `-n 4` | **8736.2 MB** | **2811.6 MB** | —（贴上限被中止） | ⚠️ 不作数，只当证据 |
  | `-n 4` + `V3_PARSE_CACHE=0` | **5279.4 MB** | **3308.6 MB** | **246.9 s** | ✅ 唯一有效的完整并行读数 |
  | `-n 1` | 3815.4 MB | 3785.7 MB | 605.5 s | ❌ 作废（外部污染 + 482 条 setup 错误） |

* **预算**：每 worker 峰值 ≤ **512 MiB** 且 整套峰值 ≤ **1024 + n×512 MiB**（§6）。
  **当前基线不达标**：`-n 4` 那一档实测整套 8736.2 MB（上限 3072 MB）、每 worker 2811.6 MB（上限 512 MB）。
* **主犯前三名**（§7）：`pdx.cache` 的**磁盘分片视图**（+2402.5 MB） >
  `analyze.game_analysis()`（+2523.4 MB）> `analyze.mods_analysis()`（+2364.0 MB）。
  三条都有单点复算命令，不是推断；而**两臂判决实验**证明这三者其实是**同一份冗余容器**
  被三条路径各触发一次 —— 真把全树结果留着也只值 **605.7 MB**（§7.1.1）。
* **另有一个瞬态**：某个 **2.47 MB** 的地图脚本解析一次要 **~1.1 GB**（≈450 倍放大，§7.6），
  它给「每 worker ≤512 MiB」设了第二个必要条件（§6.5）。
* **默认并行度**：`-n auto` 仍由 `pyproject.toml` 启用，但 `tests/conftest.py` 会根据
  可用内存和 CPU 动态限制 worker；可用内存不足时自动降到 1，避免把机器推到 OOM。

## 2. 口径：三个数各是什么

### 2.1 整套峰值 `peak_total_mb`

**定义**：以被测命令进程为根的那棵**进程树**，在任一采样时刻的**常驻内存（RSS）之和**，
取所有采样点的最大值。含义是「这台机器必须同时拿得出多少物理内存」。采样间隔 250 ms。

为什么是「树」而不是「机器上所有 python」：**上一轮就是这么量的，而那个数不可复算**。
旧采样器（`tools/out/mem/measure.ps1`）用 `Get-Process -Name python` 求和，于是
`probe-chain.peak.json` 里那个 `5057.6 MB / nproc=4` 混进了**与本测量无关**的 python 进程；
换一台机器、换一个时刻就不再是同一个数。所以本脚本只数**被测命令的子树**，
并在产物里记下当时**全机器**的 python/游戏进程快照（`concurrent_before_mb0`）以便追溯。

采样法的固有局限与交叉验证：

* 它是**下界**（可能漏掉两次采样之间的尖峰）→ 同时报一个漏不掉的**上界** `sum_hwm_mb`
  （每个进程自己活到那一刻的 OS 高水位之和；worker 不会同时站在各自最高点，所以是上界）；
* 两者接近 ⇒ 峰值是「一起到达的」；差得远 ⇒ 峰值是**错峰**的，
  这时**不能**用「每 worker 峰值 × worker 数」去推整套峰值。

### 2.2 每 worker 峰值 `per_worker_peak_mb`

**定义**：每个 worker 进程自己活到那一刻的 OS 高水位 —— Windows `PeakWorkingSetSize`、
Linux `VmHWM`（macOS 没有这个计数器，退化成「存活期间最大采样值」，产物里用
`peak_source: hwm|sampled` 标出来，跨平台比数之前先看这个字段）。

为什么这个数最重要：**它不随并行度变**，所以它是唯一适合「优化前 vs 优化后」「本机 vs CI」
比较的那个；整套峰值随 `n` 线性变，换了并行度就没法比。

外部的每 worker 峰值是「存活期间**最后一次观测到**的高水位」，
所以它天然 ≥ worker 自报的值（`--inproc` 时在 `sessionfinish` 那一刻读到的）。
两者之差就是采样间隔那一段的尾巴 —— 冒烟跑法（`-n 1`、单模块、2 秒）上实测差 **7.7 MB**
（外部 68.4 / 自报 60.7）；**完整套件下这个交叉验证没跑**（`n4-inproc` 那组没赶上窗口，
见 §9.1 第 7 条），所以正式数字只有一个来源：**外部采样**，产物是 `<tag>.procs.csv`。

### 2.3 总耗时 `wall_s`

**定义**：被测命令从起进程到退出的墙钟时间。它和内存一起报，
是因为「内存达标」不能靠降速换：§6 的判据里带着退出码与用例数，
而耗时单独列出来供人判断是否出现了「用时间换内存」的退化。

### 2.4 进程角色怎么判（这一步比看上去难）

本机的 `.venv\Scripts\python.exe` 是一个 **launcher**：它 `exec` 出**同名同命令行**的子进程，
自己常年只占 4 MB，`os.getpid()` 落在子进程里。而且 **xdist 起 worker 也经由它**，
于是一棵树长这样：

```
launcher(4MB) → 真 pytest(-n 4 的 controller) → launcher(4MB) → worker   ×4
```

按「第几层子进程」判角色会把 worker 当成 controller（实测踩过：`-n 1` 的冒烟跑法里
worker 被标成 `root`，每 worker 峰值直接读成 0）。现在的判据是正向识别：

1. **候选** = 高水位 ≥ 24 MiB 的 python 进程（launcher 永远只有 4 MB，进不了候选）；
2. **真身（controller）** = 候选里最浅的那个；
3. **worker** = 真身的后代候选，且**父就是真身**，或**父是 python 但不是候选**（launcher 中转）
   而祖父是真身；再要求存活 ≥ 真身寿命的 30%（测试自己起的 `v3` 子进程只活几个百分点）；
4. 真身的 python 祖先是 `launcher`，其余是 `helper`。

这条分类**不是自证**：`--inproc` 时每个 worker 会在退出前把自己的 pid / 峰值写进
`tools/out/mem/inproc-*.json`，脚本逐个比对，对不上就报
`classify_match: false` 并打印警告 —— 判错了不会悄悄混进基线。

### 3.2 测量时无并发重活（合约要求，附状态记录）

合约要求：测量时**不得与并行套件、`v3 verify`、游戏同时跑**。做法是三层：

1. **开工前**：脚本自己查（任何 ≥ 200 MB 的 python 或任何 `victoria3` 就**等着不跑**，
   最多等 `--wait-quiet-s`；等不到就**报错退出**，不静默开跑），并且要求空闲物理内存
   ≥ `--min-avail-mb`（默认 4096 MB）；
2. **每一组开工前重新查一次**（不是一个窗口开头查一次就算）；
3. **开工/收工**各记一份全机器 python/游戏进程快照进产物
   （`concurrent_before_mb0` / `concurrent_after_mb0`），出问题能追。

**本轮的真实执行情况（如实记录，不粉饰）**：

* `n4-nocache` 那一组是**干净**的（开工/收工快照里只有 4 MB 的 launcher 壳）；
* `n4` 的两次尝试都撞上了外部重活，并因此把可用物理内存打到 515 MB / 43 MB 被看门狗中止；
* `n1` 那一组作废（外部重活 + 482 条 setup 错误，见 §5.3）；
* 若干 `one` 步骤的 `concurrent_at_start` 记着 **200–224 MB 级**的并发（读 JSON/文档的进程），
  对 2.4 GB 量级的结果影响约 8% —— **那些行按「有并发、未重测」标注**，不当干净读数。

⇒ 这三条记录本身就是「状态记录」这一要求的执行结果；后续要拿干净整数的人
（`t26`）应当**先看快照字段再引用数字**。

## 5. 基线数值与每一组的状态判定

> 口径纪律：**只有「跑完 + 无并发重活 + 缓存状态一致」的组才是基线**。
> 被中止的组保留读数，但必须标成「不作数」；被污染的组整组作废。
> 下面每一行都写了它属于哪一种 —— 引用数字前先看「状态」列。

### 5.1 三组必测对照（本轮实测）

| 组 | 命令（逐字） | 整套峰值 MB | 每 worker 峰值 MB | 总耗时 s | 状态 |
|---|---|---|---|---|---|
| `n4` | `-m pytest tests -q -n 4` | **8736.2** | **2811.6** | —（没跑完） | ⚠️ **不作数**：48.3 s、进度 30% 时可用物理内存掉到 **43 MB**，看门狗中止；两次尝试分别掉到 515 MB / 43 MB |
| `n4-nocache` | 同上 + `V3_PARSE_CACHE=0` | **5279.4** | **3308.6** | **246.9** | ✅ **有效**：100% 跑完，无并发重活（失败 18 条逐条归类见 §5.5） |
| `n1` | `-m pytest tests -q -n 1` | 3815.4 | 3785.7 | 605.5 | ❌ **作废**：482 条 `FileNotFoundError` 级联（`pytest-1590\popen-gw0` 消失，见 §5.3）＋当时还有外部重活（1–1.5 GB 级的缓存实验） |

附加读数（每 worker 峰值明细，来自各组 `<tag>.procs.csv`）：

| 组 | worker 峰值（MB，按大到小） |
|---|---|
| `n4` | 2811.6 · 2576.3 · 2542.2 · 1370.7 |
| `n4-nocache` | 3308.6 · 1765.9 · 1730.3 · 1711.8 |

两个数一起读才能看懂形状：

* **整套峰值**：`n4` 8736.2 ≫ `n4-nocache` 5279.4（差 1.65×）；
* **每 worker 峰值**：`n4` 2811.6 **<** `n4-nocache` 3308.6（**反过来的**）。

### 5.2 「峰值同步化」——本轮最要紧的一条结论

上表那对反号不是噪声，机制是清楚的，而且**可复算**：

1. 磁盘层的分片视图让「读到一个文件」变成「把整片 AST 装进来」（§7.1），
   而读 16 片的全部代价只有 **2.8 s**（全部 16 片从盘读回；对照：重新解析整棵树 65 s）；
2. 于是 `-n 4` 的 4 个 worker 在开跑后 **几秒内几乎同时**进入重状态，
   峰值在时间上**叠加**（8736 MB ≈ 4 × 2.2 GB）；
3. 关掉磁盘层后，每个 worker 得自己慢慢解析 65 s，**重状态被摊开**，
   于是「每 worker 更高（3308.6）、整套反而更低（5279.4）」。

**这条结论的推论是反的，t12 必须按它办**：单看「每 worker 峰值」会得出「关缓存更差」，
单看「整套峰值」会得出「关缓存更好」。**修好分片加载（按需单条取）之后，错峰会被重新引入或削弱**，
所以修完必须**重测整套峰值**；若出现「每 worker 降了、整套没降」，要如实报告并解释机制，
不许只挑好看的那个数。

### 5.3 为什么 `n4` 没有完整数、`n1` 为什么作废

* **`n4` 在本机跑不完，两次都一样**：15.80 GiB 的机器上，`-n 4` 的树峰值就已经到
  8.7 GB，而系统本身（DSH/编辑器/浏览器，约 4–5 GB）压着 —— 两次分别把可用物理内存
  打到 515 MB 与 43 MB。这不是工具问题，是**基线本身的结论**：
  **当前实现下，默认并行度那一档在这台机器上贴上限**。按「不许把机器压到 OOM 边缘」的
  约束**不再尝试第三次**；完整并行基线退到 `-n 2` 或换机器。
* **`n1` 作废的两条独立证据**：① 计数是 `failed=7, passed=1143, skipped=8, error=482`，
  那 482 条 error 全是同一个 `FileNotFoundError` 级联
  （pytest 的 basetemp 子目录 `%TEMP%\pytest-of-28905\pytest-1590\popen-gw0` 在跑的中途不见了；
  跑完后 `pytest-1590` 存在但**是空的**，磁盘还有 269 GB 空闲 —— 不是磁盘满，也不是内存问题）；
  ② 它开跑的时刻撞上了外部重活（1–1.5 GB 级实验）。两条都足以让它不能当日志里的「地板」。
  串行档位的干净数值留给后续补测。
* 结论：**本轮真正可用的完整并行读数是 `n4-nocache`**；`n4` 的 8736.2 MB 只能当
  「贴上限证据」，不能当基线。

### 5.4 旧默认并行度基线（历史记录）

本节保留 2026-09-25 优化前的 16 worker 读数，用于解释为什么需要内存护栏。
当前默认行为以 §1.1 的动态 worker 复测为准；不要把本节的 16 当成现行配置。

`-n auto` 在这台机器上是 **16 个 worker**。`-n 4` 已经顶到上限，16 worker 只会更差
（同一份保留策略 × 4 的并行度），而按硬约束不许把机器压到 OOM 边缘；
加上它是**默认档位**、换了 `-n` 就等于换了被测量的东西（§8 第 1 条）。
所以本文件不给 `-n auto` 的数值，只给一条判据：

```
n = 4 时整套峰值就已经是 8736.2 MB（且被中止）
目标（§6）：n = 4 → ≤ 3072 MB；n = 16 → ≤ 9216 MB
也就是说：即使按 16 worker 的目标上界算，当前实现在 n = 4 就超了
```

### 5.5 失败清单归类（三类之和必须等于失败总数）

`n4-nocache` 的 18 条失败里，**没有一条与内存工作有关**，逐条归类如下
（三类之和 7 + 11 + 0 = 18）：

| `n4-nocache`（cache off） | **5279.4 MB** | **3308.6 MB**（**反向更大**） |

—— 逐组产 `<tag>.summary.json`（两个峰值）、`<tag>.samples.csv`（时间线，可看「同时进入重状态」）、
`<tag>.procs.csv`（逐进程峰值）。

**⇒ 对 t12 的约束（本轮已兑现）**：任何降低「分片加载体量」的改法都可能**同时削弱错峰、把整套峰值顶回去** ⇒
**修完必须重测整套峰值**，不许只报每 worker。**兑现方式**：修复后同命令同配置
`n4-nocache` 整套 5279.4 → **3472.1 MB（−34.2%）**、每 worker 3308.6 → **1938.2 MB（−41.4%）**
—— **两侧同降**，未出现「每 worker 降、整套没降」（判决命令 `mem_baseline.py --compare`，退出码 0）。

#### 5. 「2.4 GB 是不是地板」的判决实验（两臂，各自独立进程）

| 臂 | 处置（产物里的 `arm_counts`） | 终值 resident | 峰值 | 耗时 |
|---|---|---|---|---|
| `one retain` | 解析 6252 个、**全留在一个列表里**（留 6252 / 丢 0） | **605.7 MB** | 1453.7 MB | 18.9 s |
| `one drop` | **同样解析、用完即丢**（留 0 / 丢 6252） | **62.5 MB** | 1189.8 MB | 24.5 s |

**判决**：① 表示本身很瘦（全树结果真留着也只值 605.7 MB）；② 分配器**会**归还
（`drop` 从峰值 1189.8 回落到 62.5）⇒ **那 2.4 GB 既不是「表示开销」也不是「freed-but-retained」，
而是「被持有的结果」** ⇒ **不是地板，可修**（t12 已修：分片视图 2402.5 → 4.3 MB）。
**两臂各起一个独立进程**（不许同会话前后跑，否则 B 臂继承 A 的堆高水位、两支分不开）；
采样前 `gc.collect()`；**结果计数写进产物**。复算：`one retain` / `one drop`。

⚠️ **P13 记账**：本轮**没有静默换尺** —— 旧判据（每 worker ≤512 MiB、整套 ≤1024+n×512 MiB、
或相对完整基线降 ≥30%）原样保留；实测结果是**降幅那条过（−34.2%）、预算那条未过**
（3472.1 > 3072，超 13%），两条**分别留档**（§5.10）。要改口径属大方向决策，由队长裁。

## 6. 预算判据（可自动判定）

### 6.1 判据本体

```
判据一（每 worker）  per_worker_peak_mb ≤ 512 MiB
判据二（整套）       peak_total_mb     ≤ 1024 + n × 512 MiB     （n = 实际 worker 数）
判据三（不许作弊）   被测命令退出码 = 0，且 passed 用例数 ≥ 参考基线的同组数字
```

一条命令判决（退出码 `0` = 达标 / `1` = 不达标 / `2` = 缺产物）：

```powershell
.venv\Scripts\python.exe tools/probe/mem_baseline.py check `
    --index tools/out/mem/baseline.json --reference tools/out/mem/baseline-优化前.json
```

代入三档：`-n 1` → 整套 ≤ 1536 MiB；`-n 4` → ≤ 3072 MiB；`-n auto`(16) → ≤ 9216 MiB。

### 6.2 X = 512 MiB 的 why

* **必要性下界（实测，不是估计）**：单进程里**真正必须**常驻的东西是这些 ——
  解释器 + 标准库 38.9 MB、pytest + pdx 导入 ~2 MB、语料路径表 +14.6 MB、
  语料正文夹具 +61 MB、单个文件解析出的 AST（游戏最大的脚本文件也 < 10 MB）、
  分析结果对象（`deep` 实测：`ga`/`ma`/`ca` 见 §7）。
  合起来是 **约 130 MB 量级**（复算：§9 的 `one imports` / `one corpus_texts`）。
* **512 = 3.9 × 那个下界**：留给 CPython 分配器的碎片与「峰值错位」
  （不同阶段的高峰不在同一时刻，RSS 不会回到低点）。定得比下界高、比现状低一个数量级，
  是为了让判据**既能抓住真退化，又不逼人去做危险的省内存手术**。
* **可达性**（关键，否则 512 只是拍脑袋）：把「永久保留」改成「不永久保留」后实测峰值见
  §7 的 `--janitor-s` / `--evict-every` 两列；它们都在 512 以内或量级相当
  ⇒ **不需要减少任何计算、不需要跳过任何用例**，只要不再把整棵语料 AST 永久留在内存里。
* **与并行度的关系**：15.80 GiB 的机器上默认 `-n auto` = 16 worker，
  16 × 512 MiB + 1024 MiB 车头 = 9.0 GiB = 物理内存的 57%，剩下 6.8 GiB 够 OS 与编辑器，
  不会触发换页。这也是**为什么不能把 X 定得更高**：X 是「乘上 16 之后仍然安全」的那个数。

### 6.3 Y(n) = 1024 + n × 512 MiB 的 why

* **为什么上限要随并行度走**：worker 之间不共享内存缓存，每个 worker 都要各自装一遍
  （`pyproject.toml` 里那段 `--dist loadscope` 的注释就是为这件事写的：按模块分组把
  「重复解析」压到最小，但压不到零）。所以整套峰值**天生是 n 的函数**。
  用一个固定绝对数当上限，会同时误判两头：对 `-n 1` 太松，对 `-n auto` 太紧。
* **车头 1024 MiB**：controller 自己要做完整收集（本轮 **1638** 个用例）、转发每个 worker 的
  报告、汇总输出。实测 controller 峰值见 §5.2 的每进程表；1024 留出数倍余量，
  也刻意不把车头写成 0 —— 否则「worker 数 × X」会变成一条永远紧张的红线。
* **为什么不拿「物理内存的百分比」当判据**：那会让判据随机器变（CI 内存小、开发机内存大，
  同一份代码得到不同判决），而这条判据存在的意义正是「同一台机器、同一条命令、
  优化前后得到同一种判决」。物理内存只在**论证 X** 时用一次（§6.2 末条）。

### 6.4 「正确性第一」下这条预算不牺牲准确率

1. **被砍的全是记忆化，不是计算**：`pdx.cache` 的两层都是**纯记忆化** ——
   命中与未命中返回**同一个** `ParsedFile` 结构（`cache.py` 的不变量，
   由 `test_cache.py::test_真实语料上缓存与直连完全一致` 逐字段钉住）。
   减少保留只能改变「同一份字节从哪一层来」，不可能改变任何数值。
   这也是为什么「降内存」与「保准确」在这条路径上**不冲突**：省下来的不是精度，是冗余副本。
2. **判据自带防作弊**：判据三要求退出码 0 且 `passed ≥ 参考`。
   靠加 skip、删用例、`-p no:cacheprovider`、`--deselect` 之类把数字做小，会直接判不达标。
3. **覆盖率门禁不动**：`pyproject.toml` 的 `fail_under = 86` 是**全局兜底**；
   `src/pdx/covgate.py` 的**模块下限表**才是真正的约束，而其中
   **`pdx/cache.py` 的下限是 92.0%**（实测 94.0%）—— 动 cache.py 就是动这条线，
   且该表的纪律是「**只许上调**」。t12 的新分支要设计成可测的边界（否则那 2 个点余量很快被吃光）。
4. **产物口径不动**：`v3 verify` / `v3 check-outputs` 必须在优化后复跑（阶段出口判据的守卫），
   它们核的是**游戏真值**，与内存无关 —— 一旦内存优化把缓存身份判定弄坏，
   这两个会红（见 §7.1 末条的身份判定风险）。

### 6.5 判据分层（队长 2026-09-25 裁定）与实测判决

一个绝对数字（X=512 MiB）会同时被两件事绑架：本机只有 15.80 GiB、以及一个**不在本卡范围内**
的瞬态（§7.6）。所以判据改成**四层**，主判据是**相对降幅** —— 它是相对量，不受机器约束绑架，
也直接对应用户那句「优化并行测试的内存占用」：

| 层 | 判据 | 本轮实测 | 判决 |
|---|---|---|---|
| **第一层（主判据）** | 同一命令下，整套峰值相对**冻结基线里唯一完整跑完的组**（`n4-nocache` = 5279.4 MB）**下降 ≥30%**，且退出码 0、用例数不减 | 见 §5.7 | 见 §5.7 |
| **第二层（子目标）** | `pdx.cache` 的**分片视图常驻 ≤ 512 MiB**，修后由 `one shards_each` 独立复算 | **4.3 MB**（修复前 2402.5 MB；队长另用 `_load_index` 直测得 4.15 MB —— 两条独立路径差 13%） | ✅ **碾压式通过**（用掉判据的 0.8%，约 560× 降幅） |
| **第三层（瞬态，只要求量准 + 定性）** | 把 ~1.1 GB 的单文件解析尖峰**钉到具体文件**，判定孤例还是一族；**本轮不要求修** | `one biggest`：**孤例** —— `dlc004…/european_dynamic_forestry_objects_generator_2.txt`（2.467 MB）把高水位从 142.1 推到 **1191.6 MB**；第二名只有 +39.9 MB | ✅ 已钉死，归 backlog（触发条件：任何 worker 的峰值预算被它顶住时） |
| **第四层（记账，P13）** | 任何一层没过，都要把「**旧判据未达标**」与新的地板/瞬态数字**一起留档**，不许静默换尺 | 本文件 + `tools/out/mem/baseline-优化前.json`（冻结副本，`tools/out/` 不入库）即那份留档 | ✅ |

**为什么第三层不修**：它是解析器/词法层的事，而**正确性第一**；在缓存层做手脚绕开它
（例如预烤全部 6252 个文件）等于把风险塞进另一条路径。所以本轮只要求「量准 + 定性 + 留档」。

**为什么不留「把 X 抬到 1536 MiB」这条路**（队长明确否掉）：抬 X 会让 `-n 4` 的整套上界变成
1024 + 4×1536 = 7168 MiB，等于**用放宽标准换达标** —— 方向反了：口径是为结果服务的，
不该为迁就现状而松。

### 6.6 X = 512 MiB 的可达性：两个必要条件（实测口径）

| # | 必要条件 | 修复后现状 |
|---|---|---|
| 1 | **不再永久保留整棵语料 AST**（分片视图 / memo 任一都不许装全树） | ✅ 已修：分片视图 2402.5 → **4.3 MB**；memo 加上界（1024 条）后 `one parse_all` 峰值 2757.4 → **291.0 MB**、耗时 752 → **11.08 s** |
| 2 | **单文件解析放大**（§7.6） | ❌ 照旧（**不在本卡 inScope**）：任何解析该文件的 worker 峰值仍 **≥1.19 GB** ⇒ 预算 X 的**逐 worker 金额**暂时不可达，但**整套降幅**（第一层）可达 |

⇒ 如实记账：**第一层（整套相对降幅）达成；「每 worker ≤512 MiB」被第 2 条顶住** ——
第 2 条进 backlog，修掉之后 X=512 MiB 才成为逐 worker 可达的目标。**不静默改尺。**

### 7.1 第一名：`pdx.cache` 的磁盘分片视图

`src/pdx/cache.py` 的 `_load_shard(index)`（第 260 行起）是**按需查一条 = 全量加载一片**：
分片是 `pickle` + `zlib` 的一整个文件，要查其中一条就得把整片解压 + 反序列化，
然后把它挂在 `_state.shards` 里**永久**（`SHARDS = 16`，`MAX_ENTRIES_PER_SHARD = 4000`，
两处都没有淘汰策略）。后果是**内存代价与「碰了几个分片」成正比，与「真正用了几条」无关**：

**实测（`one shards_each`，一次跑完 16 片；产物 `tools/out/mem/shards_each.json`）**

| 量 | 值 |
|---|---|
| 16 片合计条目 | **20,595**（有效语料 6,252 个文件 ⇒ 约 3.3× 的历史版本） |
| 16 片磁盘合计 | **103.03 MB**（压缩后） |
| 装进内存后常驻增量 | **+2402.5 MB**（进程高水位 **2514.4 MB**；`gc` 后仍是这个量级） |
| **放缩比** | **23.3 ×** —— 看 `.bin` 的体积会**严重低估**内存 |

逐片读数（`shards_each.json` 的 `rows`）显示片与片之间差别极大（0.9 → 484.9 MB），
**但那不是「有些片更省」**：进程已经握着 GB 级内存时，Windows 会开始**修剪工作集**，
后加载的片的 `Δrss` 于是被低估；所以**只有合计值与进程高水位可引用**，
逐片 `Δrss` 不能拿去算「一片值多少」。

* **独立复现**：上一轮的分步探针在**另一次运行**里测到同一件事 ——
  `shards_touch`（每片只解析 1 个文件）`Δ+2413.89 MB`、`峰值 2602.81 MB`。
  两次独立测量差 **0.4%**（2402.5 vs 2413.9），所以这不是噪声。
* 也就是说：**碰 1 个分片 ≈ 付一整片（最多 4000 条）的钱**；
  一个 worker 只要扫过整棵语料，16 片全部进内存 ⇒ 与「把整棵语料 AST 装进内存」等价。
  **这正好抵消了磁盘层存在的理由**（磁盘层是为了省内存，见 `cache.py` 开头）。
* 复算：`.venv\Scripts\python.exe tools/probe/mem_baseline.py one shards_each`
  （外加 `one shards_touch`——「只解析 16 个文件」就能看到同一堵墙）。

#### 7.1.1 这 2.4 GB 是**冗余容器**，不是「结果本身的地板」（两臂判决实验）

有人会顺手把「2.4 GB」解释成「全树 AST 本来就这么大，删不掉」。**这个解释是错的**，
两臂实验（`one retain` / `one drop`，**各自独立进程**，唯一差别是留不留结果）把它判死了：

| 臂 | 处置 | 终值 resident | 峰值 | 耗时 | 复算 |
|---|---|---|---|---|---|
| `retain` | 解析 6252 个、**全部留在列表里**（留 6252 / 丢 0） | **605.7 MB**（181→230→297→387→441→498→606，**单调爬升**） | 1453.7 MB | 18.9 s | `one retain` |
| `drop` | 同样解析 6252 个、**用完即丢**（留 0 / 丢 6252） | **62.5 MB**（73.7→58.2→59.9→61.2→61.2→63.0→62.5，**全程走平**） | 1189.8 MB | 24.5 s | `one drop` |

两臂都走 `pdx.parser.parse_file`（**绕开两层缓存**），所以差别只有一个：留不留。

**三条判决**：

1. **表示本身很瘦**：真把全树 6252 个解析结果都留着，也只有 **605.7 MB**
   ⇒ 分片视图那 2402.5 MB 里，**约 4 倍是冗余**（同一份结果，两个容器同时驻留：
   `_state.shards` 的整片 + 随后解析/请求到的那些）；
2. **分配器会归还**：`drop` 从峰值 1189.8 一路回落到 62.5、`retain` 从 1453.7 收到 605.7
   ⇒ 「freed-but-retained 撑住了 RSS」这一支**不成立**；
3. **⇒ 那 2.4 GB 是「被持有的结果」，是**可修**的**：
   `retain` 的曲线是单调爬升的累积，与「一直往里存」吻合；
   而 `drop` 证明「同一份语料解析一遍」本身只要几 MB 的常驻。
   所以磁盘分片视图**不是地板**，是靶心（这也是 t12 的靶心）。

⚠️ 两臂**必须在各自独立的进程里跑**：同一个解释器里先 A 后 B，B 臂会继承 A 的堆高水位，
两支就分不开（这一条是评审员抓出来的，写进 `t26` 合约第 2 版）。

⚠️ **t12 动这里时的正确性红线**：缓存层最容易出的静默失效是**身份判定**
（`_same_identity`，2026-09-24 那次「同一棵树、两份数字」事故：`fields` 域 27,476 → 4,285，
无任何报错）与**指纹命中**被绕过。逐字段等价用例
（`test_cache.py::test_真实语料上缓存与直连完全一致`、`test_缓存不改变全语料的聚合结果`）
必须原样守绿。

### 7.2 第二名：`analyze.game_analysis()`（`ga`）

它是套件里最贵的一次计算：解析 6252 个文件 + 建 `common/` 138 个目录的条目表 +
本地化 11 种语言 + 17 个 DLC 的检查。

* **实测**：常驻 **+2523.4 MB**、进程峰值 **2697.0 MB**、**40.6 s**（复算 `one ga`）。
* 它的增量**几乎整份是第 1 名那一层被它拖进来的**（解析满语料 ⇒ 16 片全装进内存）；
  §7.1.1 的两臂已经证明「同一份结果真留着也只值 605.7 MB」，
  所以 `ga` 的量级是**容器**的量级，不是分析结果的量级。
* 复算时注意：`one ga` 的 `steps.jsonl` 行带 `concurrent_at_start` 快照；
  本轮那一行记着「一个 203.7 MB 的 python 进程」（队长读 JSON/文档时的进程），
  **对 2523 MB 的结果影响约 8%**，如实标注为「有 200 MB 级并发、未重测」。

### 7.3 第三名：`analyze.mods_analysis()`（`ma`）

同上口径，但输入小得多（mod 目录 + 与原版同名的几个文件）：

* **实测**：常驻 **+2364.0 MB**、进程峰值 **2462.2 MB**、**20.4 s**（复算 `one ma`）；
  与 `ga` 同量级，说明这个量级由「碰全树」决定，而不是某个函数的私有开销。
* `ca = analyze.cross_analysis(ma)` 与 `ma` 共用输入，增量可忽略。
* 该行同样带 200 MB 级并发（`concurrent_at_start`），影响约 8%，未重测。

⚠️ **「三个 ~2.4 GB 的工作负载」不等于「三个主犯」**：它们是同一份**冗余容器**被三条路径
各自触发一次（§7.1.1）。真正要动的地方只有一处。

### 7.6 一个必须单列的瞬态：单文件解析放大 ~450×

| 臂 | 检查点 3000 时的峰值 | 检查点 4000 时的峰值 | 尖峰 |
|---|---|---|---|
| `retain` | 296.7 MB | **1453.7 MB** | ≈ +1157 MB |
| `drop` | 129.2 MB | **1189.8 MB** | ≈ +1060 MB |

而 3001–4000 这个区间里**最大的文件只有 2.47 MB**（区间 1000 个文件合计 11.6 MB）：

```
idx=3167  2.47 MB  <游戏>/map/map_object_data/generated/european_dynamic_forestry_objects_generator_2.txt
```

⇒ **解析一个 2.47 MB 的文件，瞬态要 ~1.1 GB（≈450 倍放大）**。
这不是常驻（`drop` 之后立刻回落），所以它**不进前三名**；但它给任何「解析全树」的工作

`corpus_files` 的用例每条都会碰它。

* **复算**：`one drop`（或 `one retain`）的 `progress:4000` 行；

* **待收口**：精确定位到「就是这一个文件」需要**逐文件记录峰值增量**（t26/t12 的一次
  短实验，约 60 s）；这里给出的是**区间 + 尺寸异常**两条独立依据，不是猜。
* **对预算的意义**：见 §6.5 —— 它是「X=512 MiB 能不能成立」的第二个必要条件。

## 8. 本轮不许动的东西（冻结项）

1. **`pyproject.toml` 的 addopts `-n auto --dist loadscope` 本轮不许改**。
   理由不是「怕麻烦」，而是：这个取值是**实测出来的**（串行 314.2 s → `-n auto` 132.8 s，
   −58%），把它降下来等于用速度换内存 —— 那是把问题挪走，不是解决。
   而内存主犯（§7）是**保留策略**，与并行度正交：
   同样的保留策略下，`-n 4` 与 `-n auto` 的**每 worker 峰值**是一样的，
   差别只在「同时有多少个这样的 worker」。
   **优化必须在保持默认并行度的前提下把内存降下来**：判据二就是按 `n` 判的，
   改 `n` 既不会让判据变松，也不会让它变紧 —— 但会引起耗时的独立回归（速度那一轮的账）。
2. **不许靠少跑用例省内存**：不删用例、不加 skip/xfail、不改 `testpaths`/`python_files`、
   不用 `--deselect`/`-p no:...` 关插件。交给判据三（`passed ≥ 参考`）自动拦。
3. **不许关掉磁盘缓存层**：`V3_PARSE_CACHE=0` 那一组是**对照**，不是优化方案 ——
   关掉它会把 16 个 worker 的跨进程共享收益一起扔掉（实测全语料读盘 2.8 s vs 重新解析 65 s）。
   要动的是「它在内存里留多久」，不是「它在不在」。
4. **不许改 session 夹具的语义**：`conftest.py` 的 `corpus_files` / `corpus_texts` / `ga` / `ma` / `ca`
   可以改**实现**，但必须仍然是「整轮只跑一次的全量分析」的单一真值来源
   （`--dist loadscope` 的收益就建立在这条上）。
5. **覆盖率门禁不动**（`fail_under = 86`）。

### 9.1 已知限制（引用数字前先读这一节）

1. **采样是 250 ms 一次**：整套峰值是**下界**；`sum_hwm_mb` 是上界。两者都看。
2. **每 worker 峰值在 macOS 上退化**成采样最大值（没有高水位计数器），产物里带 `peak_source`。
3. **launcher 中转**：`.venv\Scripts\python.exe` 会再 spawn 一个自己（§2.4）。
   用别的方式量（例如直接读启动命令的 pid）会读到 4 MB 的空壳 —— 实测踩过四次。
4. **`--inproc` 会轻微扰动**：它给每个 pytest 进程加一个 0.5 s 的采样线程与一次收尾写盘
   （量级：几 MB），所以归因组单列一个 tag，**不用它当基准组**。
5. **随机顺序**：`pytest-randomly` 默认随机种子，模块落哪个 worker 会变（`--dist loadscope`），
   于是整套峰值有几个百分点的抖动。产物里记了 `randomly_seed`；
   要做可比的 A/B 就用附加组 `n4-seed1`（`--randomly-seed=1`）。
6. **磁盘缓存状态是条件之一**：同一台机器、同一条命令，缓存里有哪些分片会改变读数。
   产物里 `cache_before` / `cache_after` 记着当时的片数与字节数。
7. **本轮没跑到的三项**（留给 t26 的干净窗口，不影响 §7 的结论）：
   * `-n 4` 的**完整**读数（两次都在贴上限处被看门狗中止）；
   * `-n 1` 的干净读数（那一组作废）；
   * `n4-inproc`（逐 worker 自报值对完整套件的**交叉验证**）—— 只在 2 秒的冒烟跑法上验过
     （`classify_match=true`，逐 pid 对上）。
8. **两臂必须在各自独立的进程里跑**（§7.1.1）：`one retain` 与 `one drop` 是两次
   独立启动的进程，`steps.jsonl` 里各有自己的行与结果计数（`arm_counts`）。
   ⚠️ 该文件早期的 `started_at` 字段是在**跑完之后**求值的（其实是结束时刻，
   曾造成「两臂时间线重叠」的假象）；现在已拆成 `started_at` / `finished_at` 两个字段。

## 10. 速度判决的测量范围与混淆项（预注册，测前写死）

* **判据（测前预注册，不许事后调）**：r = cpu_total_s(后) / cpu_total_s(前)；r ≤ 1.05 ⇒ 无回归（写出 r）；
  r > 1.05 ⇒ 再跑一对、按**两对均值**判；某对两次运行之间若 avail_mb 相差 > 1 GB、或出现外部 ≥200 MB python / victoria3
  ⇒ 该对**作废并重跑**（理由写日志）。**被测树身份**：两臂各自的 cache.py sha256[:16] + 两臂各自的 collected 数。
* **判决范围**：r 只对「**t12 的 v2 布局相对 HEAD 的 CPU 回归**」负责。t59 之后 cache.py 的热路径还会变
  ⇒ **t59 之后的树未重测**（本轮的 r 不得被说成最终数）。

* **已作废的两对**（污染事实与方向见 collision.md §12/§14）：第一对（A 臂被 t54 的短命令扰）、第二对（A2 被外部
  projects/quant 的 python 与验证员 t55 短批次扰，两条都抬高 A2 ⇒ r 被压低 ⇒ 偏向漏判回归）。**它们不作为判决依据。**

## 11. plan B 结案：速度回归在本机今天不可判（2026-09-25 02:5x）

**触发依据 = 采样器的时间序列，不是某个 r**（tools/out/mem/t39-quiet3.log，30 s 一行）：
外部 projects/quant 的 python 以约 30 s 周期爆发 —— 02:46:25 foreign=0 → 02:46:55 foreign=10（每个 200–240 MB）
→ 02:47:25 foreign=0；更早还有 02:43:52/02:44:23 连续两次干净、02:44:54/02:45:24 各 1 个 200+ MB。
条件 ③ 要求**连续 3 次干净（约 90 s）**，而一对要跑**约 32 分钟** ⇒ 「3 连干净」的窗口**存在，但覆盖不了一对**；
按 §10 的作废规则（其间出现外部重命令 ⇒ 作废），这一对**大概率会被判作废**。

**判决**：**「速度回归在本机今天不可判」**（与阶段 4「0.5 ms 今天不可判」同型，属预注册允许的合法收尾形态）。

**纪律核对（三条都守住）**：判据与阈值（r = cpu_total_s(后)/cpu_total_s(前)，r ≤ 1.05 判无回归）**原样保留、未事后调整**；
两对已作废（污染时间线见 collision.md §12/§14），**未把任何污染对当证据**；**未用**「估算影响 <1%」代替证据。

**要拿到最终数需要什么**：另开一对（A/B 同配置、两臂同一种测量法），并预留一段**≥35 分钟**的全机器安静窗口；
两臂身份按 cache.py sha256[:16] + 各自 collected 数写死（口径见 §10）。

## 12. 结案后的有据残留（按 P14 形态：压力 / 为什么现在测不了 / 什么时候能测）

> 本节只登记「**不是本轮出口判据**、但必须留下可复算入口」的三件。判据与阈值一字未动，也不为它们占实机窗口。

* **R1 · `MEMO_MAX_ENTRIES=4096` 灵敏度跑（未做）**。**压力**：内存层上限同时决定内存与速度，而 `V3_PARSE_MEMO`
  是唯一「不改代码就能调它」的旋钮（`:data:`MEMO_ENV`` 的 why 段）—— 要回答「慢的那部分里有多少是上限造成的」，
  就必须拿上限放大版与默认版做一次同配置对照。**收益**：把「上限取 1024」从一次设计选择变成一条**有读数**的选择
  （今天它只是一个未经测量的默认值）。**为什么现在测不了**：它要一对同配置 CPU 对照（约 32 分钟）加一段全机器
  安静窗口，而本机今天拿不到安静窗口（依据 = §11 的采样器时间序列：外部以约 30 s 一次爆发）。

  ⇒ 交付物不受影响；`tests/test_cache.py::test_内存层有上限` 覆盖的是**默认路径**。

* **R3 · 测量工具的三条口径缺口（未修，均在 `tools/probe/mem_baseline.py`）**。① `foreign_ge200mb` / `foreign_heavy`
  **不排除调用者自己的进程树**（实测把 A2 臂自己的 4 个 worker 当成了「外部」，见 `tools/out/mem/collision.md` §13）；

  ⇒ 两次快照之间出现的他人重命令**抓不到**，于是「期间有没有别人」在产物侧**不可自动判定**

  中途改工具会让两臂**不是同一种测量法**（那正是 §10 作废规则要防的）。**什么时候修**：测量冻结解除后开小卡；
  修法已写死在 `collision.md` §13 与 §12(a)（外部判据排除被测树；把「外部 ≥200 MB 进程数 + 本树 CPU」按采样

## 13. 「内容进键」的成本：**预注册**的判据（t59，**测前**写死）

**背景**：`t54` 的独立验证（`docs/reports/缓存跨代读-独立验证.md` §5）证明：磁盘缓存的键
`sha256(路径 \0 mtime_ns \0 size \0 引擎指纹)` **不含内容成分** ⇒ 同路径 + 同 `mtime_ns` + 同 `size`
而内容被改时会命中**旧树**（不报错、不写日志）。它给的候选修法之一是把内容加进键（例如「首 256 B + 尾 256 B
+ size 的摘要」）—— 代价是**命中路径从 1 次 `stat` 变成 `stat` + 两次小读**，而这条路径在全量分析里是热点
（数千个文件 × 每次运行）。按 P5/P7，**不许凭感觉采用或否决** ⇒ 先把判据写在这里，再测、再判。

**判据（看到数之后一个字都不许改）**

* **T1（决定性·绝对量）**：数千文件量级的命中路径**总增量 ≤ 0.65 s**。
  理由：分母取本仓实测的全量解析 wall（65 s 量级，见 §5 的 65 s 数据点），1% 是这类整树任务的运行间波动量级
  （t39 已实测：同类任务的 wall 能被外部负载抬到 3.9×）⇒ 超过 1% 就不再是噪声。
* **T2（护栏·相对量）**：**单文件增幅 ≤ 5×**（1 次 `stat` ≈ 2–3 µs ⇒ 允许 ≤ 15 µs/文件）。
  理由：短命令（`v3 evidence` 那种只解析几个文件的）不该被拖慢到可感知；20 个文件 × 15 µs = 0.3 ms。
* **T3（覆盖性）**：该修法要能挡住 `t54` §5 的反例才算**关闭**；若只挡首尾两段、**中间段等长改写仍漏** ⇒ 记**收窄**。
* **判决规则**：**采用 ⟺ T1 ∧ T2 ∧ T3=关闭**；若 T3=收窄 ⇒ **不采用**（代价照付，而「不覆盖」那段文档仍得留着）。
* **量具**：同一份语料、同一进程、热缓存，`stat` 版 vs `stat + 首尾 256 B` 版各跑 3 遍取中位数；
  两版都算同一条 sha256（差别只在读盘次数）。语料与 N 现读、写进结论。

（下面的实测与判决在**测完之后**追加，判据本身不再改动。）

### 13.1 实测（2026-09-25 04:5x，本机；语料 = 游戏树全部 `.txt`，**N = 3,758**，其中 `common/` 下 3,028）

量具：同一进程、热缓存、每个变体跑 3 遍取中位数；都算同一条 sha256（差别只在读盘次数）。
量的就是命中路径上「算一把键」的代价。

| 变体 | 3,758 文件中位数 | µs/文件 | 相对倍数 | 外推到 6,250 文件的**增量** |
|---|---|---|---|---|
| **A** 现状：1 次 `stat` | 0.0329 s | 8.76 | 1.00× | — |
| **B** 判据里写的那版：`stat` + 首尾 256 B（缓冲文件对象） | 0.2559 s | 68.08 | **7.77×** | **+0.371 s** |
| **B2** 最省的写法：`stat` + 首尾 256 B（裸 fd + `os.lseek`/`os.read`） | 0.1512 s | 40.23 | **4.59×** | +0.197 s |
| **B3** 更弱：`stat` + 只读首 256 B | 0.1444 s | 38.43 | 4.39× | +0.185 s |

（另一遍独立复量：A 9.74 µs / B 72.11 µs / **7.41×** / +0.390 s —— 两次一致，B 的倍数在 7.4–7.8×。）

### 13.2 按**预注册**判据的判决：**不采用（否决）**

* **T1（总增量 ≤ 0.65 s）**：B = **+0.371 s**（6,250 外推）⇒ **过**；
* **T2（单文件 ≤ 5×）**：B = **7.77×**（复量 7.41×）⇒ **不过**；B2/B3 因换写法勉强过（4.6×/4.4×）；
* **T3（覆盖性要「关闭」）**：首尾各 256 B **只覆盖文件两端** ⇒ **中间段**的等长改写（改哪一段都行，
  只要长度不变）两版算出的摘要**完全相同** ⇒ 仍会命中旧树 ⇒ **只是「收窄」，不是「关闭」**；
* **判决规则**（采用 ⟺ T1 ∧ T2 ∧ T3=关闭）：**不采用**。

**理由（三条，按重要性）**：
1. **它换来的不是「关闭」而是「收窄」**：真正要挡的是「内容变了而键没变」。首尾 256 B 挡住了
   「改开头/改结尾」，中段等长改写照漏 ⇒ **模块文档里那段「不覆盖」仍然得原样留着** ⇒ 代价付了、
   承诺还得照旧写。要**关闭**只有一条路：**全内容摘要**（每次命中都要把整个文件读一遍）——
   代价远大于 B2，等于把「命中路径」变成「接近重新读一遍」。
2. **判据里那一版实现实测超标**：7.4–7.8× > 5× 护栏（虽然 T1 的绝对量只有 0.37 s，这正是
   「小文件短命令」与「全量整树」两种用法要分开看的地方——短命令按**单文件**判，整树按**总量**判）。
3. **触发条件本身极窄**：需要「同路径 + 同 `mtime_ns` + 同 `size` 而内容被改」。本仓工具链自己不制造
   这种状态（`copy2`/`utime` 只用于原样备份与还原）；真实风险是**粗粒度文件系统**（FAT/exFAT 2 s、
   部分 SMB）上的同 tick 等长改写。⇒ 定 **medium**，用**文档明写 + 两条逃生口 + 一条边界用例**
   收口，而不是为它给每次命中加两次读盘。

**因此本卡采用 `t54` §5.4 的**第一条**修法（≈0 成本）：措辞改成「世代键 / 世代自证」，
不覆盖的情形与两条逃生口逐字写进模块文档「正确性」一节；`cache.py` 的行为**零改动**。
（若将来要关闭这条通道，判据与量具就在本节：先按 T1/T2 复测「全内容摘要」版，再判。）
