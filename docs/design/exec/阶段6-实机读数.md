### 3.2 判据漏洞（原始证据 + 修法）：三帧同哈希，却写了四行 ✅

**硬事实（可复核）**：盒①第二遍（02:23:17–02:25:31，摘要 `stage6-ui-20260925-022317.md`）的
`19-main-menu.png` / `20-setup-screen.png` / `21-rules-window.png` **sha256 完全相同** ——
`fa2fab91382e940dba548f183a30d7e0c7f5215907039c3309e7abe9f2e2e2b5`，均 3,832,482 B：
三个"不同的步骤结果"其实是**同一张「初始化游戏……」载入画面**。而那份摘要里 L4/L5/L6/L7
四行都写了「✅ 帧」。这是**判据太弱**的原始证据（不是驱动逻辑错），必须留着。

**为什么会这样（判据测错了对象）**：
- 起步 settle 用的是「`debug.log` 连续 30 秒不变 ⇒ 就绪」，但**载入期引擎不写
  `debug.log`**（它在读资源）⇒ 这条判据在载入期**永远说就绪**；
- 载入画面是**静态大图**（省略号动画只差 193 字节：`22-rule-sitai.png` = 3,832,675 B）；
- 抓帧那一步只证明了「截了一张图」，没证明「图里是目标 UI」。

**修法（改的是判据与驱动，口径与判据阈值一个字不改）**：
1. **载入画面基准帧进仓库**：`tools/probe/sitai_ui/loading-ref.png`（就是那张
   `fa2fab91382e…`，从被误标的 `19-main-menu.png` 原样存下来的**原始证据**）。
   每步抓帧先比它：帧间比例平均差 ≤ `LOADING_DIFF = 0.01` ⇒ 判「还在载入」，继续等；
   到 `LOAD_TIMEOUT = 300 秒` 还没过 ⇒ **抛错**，不写 ✅。
2. **点完之后等画面真的变了**（`wait_changed`）：拿上一步画面的 64×36 灰度指纹对比，
   `CHANGE_TIMEOUT = 90 秒` 内没变 ⇒ 判「这一击没生效」并抛错。
   **帧滞后于点击**是实测坑：第三遍 L5 拍到的是主菜单 —— 点对了，只是还没画出来。
3. 抓帧前一律 `ensure_foreground(force=True)`：实测点完之后会被别的窗口抢前台，
   而 `screenshot` 会（正确地）拒绝抓被遮挡的屏幕。
4. **外部负载必须记进摘要**：驱动加了 `--note`（可给多次），第四遍写的是
   「projects\quant 的 python 2 进程 / 合计 114 MB（02:34:59 实测）」。理由（队长 02:29）：
   不记负载，事后谁也分不清「帧不对」是驱动错还是环境扰动。

⚠️ **盒① 在第四遍读数出来之前不算过**：第四遍要证明「`19/20/21` 三帧**互不相同**、
而且**都不是载入画面**」。在那条成立之前，本页不写「盒① 过了」。
