# 发布生成树迁移核对

## 已可执行的前序核对

预检要求传入物理工作树根目录和前序 commit 对象的完整 ID。它使用该工作树自身的 Git 索引，逐件检查 stage、文件模式和对象 ID，拒绝生成项的 intent-to-add 状态，在内存解码恢复用 blob 后重算 Git 对象 ID 和 SHA-256。当前 Mod 树的实际路径拼写、空目录和拟新增路径共同参与 Windows 路径占用检查，拟新增父目录通过 NTFS 短名指向现有路径时也会拒绝。此结果对应本次读取时段，实际事务在写入前仍须复核。

`tools.ci.generation_transition` 接受完整的前序提交、新候选的仓库生成锁和独立评审固定的该锁 SHA-256。它只向标准输出写 JSON。前序提交必须在当前 HEAD 的历史上，其受控输出与当前 HEAD、Git 索引及工作树相符。逐件核对 Git blob、本机可恢复对象与仓库编码 SHA-256，并保留每个路径的增、删、改、留以及新旧摘要。历史锁、当前锁、删改过的用户文件、额外文件及路径冲突有差异时返回非零。可先用同一份历史锁演练全部保留。[实现](../../../tools/ci/generation_transition.py) · [合成 Git 历史测试](../../../tests/test_generation_transition.py)

```powershell
$env:PYTHONPATH = (Resolve-Path src).Path
python -B -X utf8 -m tools.ci.generation_transition --repo <待迁移仓库> --previous-commit <完整前序提交> --successor-lock <候选仓库锁> --successor-sha256 <已复核摘要>
```

前序以实际交接提交为准。3.4.0 正式标签指向 `e14d5bd1085e5727274f74c5f82876608df148f0`。在开发基线 `68d3f16921cb0545a7fe56a167135b30bd631423`，Mod 脚本、语言、封面和启动器文件与该标签逐路径相同，工程锁已随生成与发布工具变化。该开发基线的锁 SHA-256 为 `120a46582cbbf62adfe7635b52ea7ccda808adc64d31a3f644610208027907e6`，只读同锁演练核对了 100 个输出，全部保留。正式 ZIP 另含 README 和根据交付编码计算的 manifest。工具只核仓库编码的生成文件。后继包成员的来源与许可由外部固定的逐成员审查和 ZIP 回读证明。[载荷来源要求](发布载荷来源校验设计.md) · [正式交付身份](3.4.0-交付结果.md)

## 标准入口的最小切换顺序

1. 在普通生成器的**渲染之前**选择获准写点。复用生产编译器的有序贡献、只读原件身份及缺省验证，输出只取自可分发的生成器及资产。让 `distribution.package_inputs`、`decisions.build`、`_release_generation` 和玩家说明共用同一实际启用范围。旧 `package_inputs` 经过完整策略和适配器，单独改域开关或在返回后过滤文件都会先构建旧载荷。候选 `6fdf7394` 的 `tools.probes.original_company_candidate` 已隔离公司生成和包身份。其 16 项 ZIP 的 SHA-256 为 `8dae32317549ac05a31b016b08f57c063bd629d3a1a23c23ccfd9cdaa1d52b75`，当前收据为本地静态回读。正式生产需要稳定 Mod 身份、实际财政模式、正式版语言路径与功能说明。[生成入口](../../../src/pdx/distribution.py) · [生产配置](../../../src/pdx/decisions.py)
2. 新 renderer 在空目录生成候选锁与输出，先验证 11 语种、符号引用、范围和来源。原版原件只用于核实寻址、资格与事实。按每个载荷绑定仓库来源或自有生成函数、已评审输入、仓库编码摘要和交付编码摘要。封面的仓库提交可追到 `53ce21be`，其权属仍依实际资产来源凭据。对未知资产、同名未授权内容、混合原文、漏项、改名和额外项分别做拒绝回归。将完整来源单、源提交、锁摘要和 ZIP 摘要留在包外。规范化后修改的已知原文无法由精确散列拒绝，须依赖正向来源准入。[来源与恢复合同](发布载荷来源校验设计.md)
3. 独立复核新锁后运行上述只读预检。确认每一处 `retire` 有已接受的产品处置。变更前保存固定的旧 Git 提交、生成锁、每项源 blob、变更计划与当前索引状态。当前 `write_standard_outputs` 会复制整个现存树到临时目录，`decisions.write` 仅清退固定短表，`GenerationTransaction.replace` 还会暂存原字节。首次交接用隔离的空产物树与已核实的前序 Git 树组装下一提交，或实现按已核实旧对象恢复的事务适配。首次交接应避开上述两个复制点。写入前、提交时、回读失败的恢复前再核对实际归属和变更；发生并发写入则保留该写入并报告冲突。预检本身只提供当时的快照，恢复适配和故障注入是后续接线工作。[标准写入](../../../src/pdx/distribution.py) · [现有异常恢复边界](../../../src/pdx/generation_transaction.py)
4. 切换后的普通 `modgen --write/--check`、在线 `modguard`、`package` 和 `validate_package` 均调用新 renderer；验证连续两次生成及 ZIP、测试源漂移和失败回滚。离线 `modguard --offline` 检查新锁及接口，`decision-audit --offline` 对照新启用范围，`verify --fast` 跳过慢断言。它们各自的通过只覆盖相应入口。以禁止调用旧 renderer 的合成断言覆盖所有普通入口及冻结重试，避免验证过程重建旧包。[CLI](../../../src/pdx/cli_commands/release.py) · [按快照验证](../../../src/pdx/cli_commands/verification.py)
5. 复用现行 `package`、`write_zip` 和发布器的单次冻结、重试及渠道回读。发布器首次计划和执行都可能重建；有冻结包的重试仍调用 `validate_package`，冻结件丢失会回到 `_build`。每条路线都要回读同一新包并核其独立来源，执行任何渠道写入前完成拒绝检查。用合成旧树先演练干净安装、替换、版本锁和中断恢复。生产渠道及真实存档的回读按最终候选记录。旧公开包与标签留作历史引用。[发布与恢复](../../../src/pdx/publishing/runner.py) · [交付基线](工程基线-1.0.md)

逐写点的实际候选覆盖、来源核验和退役拒绝演练见[3.4.0 写点迁移清册](3.4.0写点迁移清册-结果.md)。

## 核对任意 3.4.0 后继候选

将已评审的后继生成树和原创输入提交到 Git，在包外记录审查。给核对命令提供前序工作树、前序提交、独立审查固定的后继生成锁与来源审查摘要，以及实际 3.4.0 和候选 ZIP。

```powershell
$env:PYTHONPATH = (Resolve-Path src).Path
python -B -X utf8 -m tools.ci.generation_transition --repo <前序工作树> --previous-commit <完整前序提交> --successor-lock <候选生成锁> --successor-sha256 <锁的审定摘要> --baseline-archive <正式3.4.0.zip> --successor-archive <候选.zip> --successor-review <包外审查.json> --successor-review-sha256 <独立审定摘要> --installation <锁定游戏安装根>
```

审查 JSON 使用 `schema: 2`，包括以下字段。完整的非公司脚本合成样例见[定向测试](../../../tests/test_generation_transition.py)。

| 字段 | 内容 |
| --- | --- |
| `baseline` | `commit`、`release_commit`、`generation_lock_sha256`、`archive_sha256`、`writer_inventory_sha256`。工作树前序和正式标签可以有各自的生成锁，前序输出摘要须与正式标签的 100 项输出一致。 |
| `source_commit`、`generation_lock_sha256`、`archive_sha256`、`manifest_sha256` | 完整后继提交和三个原字节摘要。将审查保存在候选提交和 ZIP 外，避免循环依赖。 |
| `members` | 按规范包路径列出 `delivery_sha256`、`origin: "original"` 和非空的 `source_files`，后者是原创 Git 路径到原字节 SHA-256 的映射。生成内容从该提交的 `mod/` 对应载荷和生成锁核定，原创输入从同一提交和锁核定。原创封面可指向自身的 Git 路径。README 另声明仓库路径 `repository_path`，并把该路径列在自己的 `source_files`。 |
| `writers` | 包含全部 981 条 `source`、`definition`、`field` 三元组和逐项 `status`。状态为 `pending`、`static_projection`、`equivalent`、`retain_vanilla` 或 `withdrawn`。 |
| `mechanisms` | 以独立审查的机制 ID 为键登记 `database`、字段 `depth`、旧 `phase`、`placement`、`transform`、实际 `prefix`、`scope`、`load_order` 和 `evidence`。 |
| `opportunities` | 独立新机会逐项记录 `member`、`definition`、`field`、`prefix`、`definition_sha256` 和 `evidence`，需要对应实际脚本位置。旧写点通过自己的行处置。 |
| `auxiliary_retirements` | 对写点清册未覆盖、且在后继中消失或换字节的脚本和本地化，以及影响加载的元数据变化登记 `path`、`reason` 和 `evidence`。 |

`static_projection` 和 `equivalent` 的 `target` 包含 `member`、`prefix`、`definition_sha256`。定义摘要按完整有序 AST 计算，忽略行号和注释。等效行另列 `mechanism`、`scope`、原值证据摘要 `original_value_sha256` 和实际候选字段 AST 摘要 `contribution_sha256`。原值摘要将锁定原版字段的值 AST 序列化为紧凑 UTF-8 JSON 后计算 SHA-256，缺省字段的值使用 JSON `null`。命令从锁定安装只读回读清册的 77 个原版路径，并按全安装冻结目录固定的原始摘要核验整个子集。机制证据应说明锁定构建上的数据库、实际加载位置、读取作用域、原值和单次贡献见证。当前核对器支持晚于原路径加载的注入或替换，以及同一路径的无前缀定义。其它顺序保持待证。候选表达式继续引用旧具名辅助值时，脚本值数据库须仍有唯一的相符定义。

`retain_vanilla` 核对原版定义和该字段的实际状态。候选覆盖同名文件时，完整有序 AST 须证明原版路径保持有效。晚加载写入不得遮蔽回退字段。`retain_vanilla` 和 `withdrawn` 需要 `reason` 和 `evidence`，撤项还需要 `authorized_by`。每个 `evidence` 包含 `path` 和 `sha256`，核对工具从已审后继提交恢复证据原件。独立评审负责审核原值事实、机制证据及产品授权，命令核对审查内的身份、适用范围与实际候选。

显式指定 `--installation`，或由 `V3_ROOT` 和标准 Steam 路径选择安装。全部待处置或静态接线的审查可离线进行。启动器名称、版本、短说明、标签、封面与安装说明由包级审查覆盖。启动器关系和引擎自定义数据纳入辅助处置。报告按路径记录增、删、改、留，并按旧三元组记录原位置与候选位置。同名文件内的定义或字段消失也会显示。存在未处置、仅静态接线或待处置辅助载荷时输出 JSON 并返回 1。验收字段分别登记冻结字节、来源和语法的 E 检查范围，以及逐写点独立 M 处置是否齐备。R 与 U 由相应的固定包实机和用户验收负责。

早期公司样件仍用 `pdx.cli modguard --writer-transition <公司候选.zip>` 查看其 15 项载荷、26 项静态接线与 955 个待处置写点。

## 正式发布预检

独立评审通过后，在包外审查 JSON 中登记 `"review_status": "independently_reviewed"`，再独立固定该文件原字节的 SHA-256。首次切换和后续原创发布均要求这一状态以及相符的独立摘要。只读核对仍可使用待审候选。

首次切换的正式生成合同将 `generation.publication_origin` 设为 `writer_transition_3_4_0`。在原有 `v3 publish` 参数上追加 `--successor-review`、`--successor-review-sha256` 和 `--previous-release-zip`，继续使用已审的同一份来源及写点审查和 3.4.0 正式包。后继锁从选定的已合并源提交恢复。计划、执行和续跑都校验标准生成器对应的同一冻结 ZIP，发布收据固定源提交、生成锁、ZIP 和独立审查摘要。

首次切换正式发布并取证后，后续的原创生产源结合已登记的切换提交使用 `original`。该路线核对同一份来源审查中的 Git、冻结字节和逐载荷来源。运行期及用户验收沿原有交付合同取证。
