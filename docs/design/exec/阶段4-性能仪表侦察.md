# exec · 阶段 4 性能仪表侦察：引擎自带的逐帧计时（`ticktask_timings`）

> 目的：给 G-EXIT-3 找一条**能量到帧级**的仪表。此前只用 `gametimer_*.tsv`，
> 它最细只到 `Day`，于是「单帧 ≤0.5ms」这条预算一直记为"量不出来"（backlog B40）。
> 结论：**量得出来**，而且引擎里已经把这套计时记在内存里，只差一条 dump 命令。

## 一、仪器在哪（exe 明文，逐串复核过计数与上下文）

| 证据（`binaries/victoria3.exe`） | 内容 |
|---|---|
| `dump_ticktask_timings [<file>]` → 默认 `ticktask_timings.csv` | 把**已经在内存里记录**的逐任务计时落盘；表头 `frame,task,milliseconds,calls,longest_lock`，行格式 `%d,%s,%llu,%u,%u`，输出 `Wrote %d rows to %s` / 失败 `Could not write %s` |
| `clear_ticktask_timings` | 帮助原文含 *"so the next dump covers only what follows"* ⇒ 可做**有界窗口**：clear → 跑 N 个月 → dump，读数不会被开局加载拉花，两次测量（原版 / 装 mod）才可比 |
| `log_ticktask_performance` → `profiling.log` | 另一条持续增长的逐任务耗时日志（时间单元 `Year/Week/Month`） |
| `run_console_action`（帮助原文 **"…, then exits"**） | 命令行能直接发控制台命令（**绕开** backlog B31 的合成键盘问题），但它**跑完即退** ⇒ 取不到"跑到目标日期之后"的 dump，只能用下面的 GUI 路线 |
| `GetPerFrameTimeExclusive` / `GetPerTickTimeInclusive` / `GetAverageTimeExclusive` / `GetPerFrameTimeInclusive` | 引擎内部本来就按帧/按 tick 计时 |

## 二、怎么把它 dump 出来（实测走通的那条路）

1. **命令行那条**只能取开局瞬间（`run_console_action` 跑完即退）⇒ **不用它**。
2. **主路（实测走通）**：挂一个只覆写 debug 模式常驻 gui 的本地 mod，加一个
   `onclick = "[ExecuteConsoleCommand('dump_ticktask_timings')]"` 的按钮 ——
   原版 `game/gui/error_deer.gui` 里就有现成写法（它的根节点 `visible = "[InDebugMode]"`，
   debug 模式常驻可见）。**用鼠标点击**（鼠标路径实测有效）。
3. **挂载前提**（backlog B39）：`content_load.json` 里混着 23 条 Workshop 时**本地 mod 不会被挂载**；
   只启用本地 mod 时正常 —— 实机那一局就是这么跑通的。
4. 跑完把本地 mod 删掉、`content_load.json` 还原成用户原来那份（本次已还原：23 条、本地条目 0）。

## 三、真实读数（第一份 dump，1,220,280 字节）

`tools/pdx/gametimer.py` 的 `ticktask_summary_lines()` 直接吃这份文件（`v3` 侧解析器已入库）：

```
文件：ticktask_timings.csv（1,220,280 字节）
  ⚠️ 文件带 UTF-8 BOM（解析用 utf-8-sig；逐字节复算时别忘）
  数据行 31458；坏行 0
  帧 502 个（59884134 → 59887140，实测步长 [6]）；任务 257 个
  每帧各任务合计：min=3ms 中位=14.0ms 均值=34.153ms max=472ms
  最重的一帧：frame 59884656 任务=237 合计=472ms 最重=RecalculateModifierNodes(67ms)
  最贵的任务：RecalculateModifierNodes  帧数=502 合计=3035ms 均值=6.0458ms 最坏=74ms 最长锁=46ms
  ⚠️ milliseconds 是整数毫秒 ⇒ 单帧分辨率 1ms；亚毫秒预算要靠窗口聚合
```

**两条对设计有直接影响的观察**：
* **最贵的任务是 `RecalculateModifierNodes`**（502 帧全部命中、合计 3035ms、均值 6.05ms、最坏 74ms）
  —— 而我们的档案**加的就是 static modifier**（压力 + 改革侧输入）。⇒ 这条任务正是"我们让引擎多花了多少"
  的**直接观测点**，比拿整帧均值去比敏感得多。
* **毫秒是整数** ⇒ 单帧分辨率 1ms。F9 的「单帧 ≤0.5ms」**不可能靠单帧读数证明**，
  必须**窗口聚合**（clear → 跑 N 月 → dump，用该窗口内 `frame` 数去除）—— 这一条要写进口径。

## 四、还差什么（G-EXIT-3 未达成）

* **对照表还没跑**：需要**原版一局 + 装我们的 mod 一局**（同一开局方式、跑到大致同一日期，
  每局 clear → 跑 N 月 → dump），报 `RecalculateModifierNodes` 等关键任务的均值/最坏帧差。
* **标准压力剧本**（`阶段4-框架化.md` §④ 要的"大战 + 连锁破产 + 革命潮"）**仍未构造** ——
  没有固定存档 + 固定指令序列，上面那种"各一局"只能算**非受控对照**，结论要标清楚。
* `log_ticktask_performance → profiling.log` 这条**未实测**（本次只走了 dump 路线）。
* **B40 的口径裁决**（F9 的"单帧 ≤0.5ms"改成什么）仍未拍板；本文件给出的事实是：
  帧级**可测**，但**整数毫秒分辨率**决定了它只能按窗口聚合用。

## 四·补 · 2026-09-23 复跑：**卡在"怎么触发 dump"上**（照实记）

`perf_compare.py` 那一套（原版一局 + 装 mod 一局）这一轮跑了两遍，都停在
`点了错误计数按钮但 ticktask_timings.csv 没出现`。把这一轮**测到的事实**逐条记下来：

### 已经查清的（可复算）

1. **按钮确实被点到了**。判据是**画面状态变化**，不是"我觉得点到了"：
   `perf-vanilla-before-click.png` 里那个按钮写着「我们有 **84** 个错误？！」，
   点完之后的 `perf-vanilla-after-click.png` 里**错误列表面板被打开了**
   （同一位置变成 5368 个错误的大面板）。⇒ 前台、坐标、真实输入这条链**是通的**。
2. **模板定位可用**：`tools/probe/zz_probe_ab/ui/btn_error_counter.png`（60x60，
   按钮左边那枚图标）拿去做多尺度匹配，**分数 1.000**、落在 (1370,500)，
   正好在实测按钮框 x 1330–1580 / y 465–555 内。⇒ "按钮在哪"从此是**每次现场测量**的。
3. **`dump_ticktask_timings` 的落点是用户目录下的 `ticktask_timings.csv`**
   （exe 明文：表头 `frame,task,milliseconds,calls,longest_lock` + 文件名 +
   `Wrote %d rows to %s` / `Could not write %s`）。跑完之后全盘找过：**没有这个文件**，
   日志里也**既没有 `Wrote … rows` 也没有 `Could not write`** ⇒ 命令根本没被执行。

### 仍然没解决的（下一步的入口）

* **覆写 `error_deer.gui` 里那个按钮的 `onclick` 没有生效**：点下去走的是**原版行为**
  （打开错误列表）。而**这一版的覆写连一条 error 都没有**
  （上一版少写外层引号时报的是 `gui/error_deer.gui:42 - '(' is not a valid
  widget/type/property`）⇒ 文件被解析了、但引擎用的仍是原版那一份。
  下一步要查的是"**为什么覆写没生效**"：本地 mod 的挂载顺序 / 缓存
  （`Documents\…\` 下有没有 gui 缓存目录）/ 或者 `error_deer` 这个面本身不吃覆写
  （阶段 4 那次成功的是"**新插**的按钮 + 颜色定位"，与这次"**改已有按钮**"不是同一件事）。
* **另一条没试的路**：`log_ticktask_performance` → `profiling.log`
  （exe 里 1 命中；持续写、不需要 dump）。若它能被某种"一次性开关"打开，
  就不必再和 GUI 按钮缠斗。

### 结论（不许美化）

**G-EXIT-3 的对照表仍未跑成。** 这一轮的净收益是：把"点没点到"从猜测变成了**可观测事实**
（画面状态差 + 模板分数），并把失败范围收窄到**唯一一处**（覆写没生效），
而不是继续在"坐标 / 前台 / 合成输入"上瞎猜。

## 四·补② · 2026-09-23 晚：**通了** —— 走**游戏内控制台**，两条仪器都拿到实物

上面那条"卡住"的记录到此为止。当晚换了入口：不再和 GUI 缠斗，直接用**游戏内控制台**。
把"控制台能不能自动用"拆成三个可分别验证的问题，三条**全部实测**（backlog B66）：

| 问题 | 实测答案 | 判据（不是目测） |
|---|---|---|
| **哪个键开控制台** | **反引号 `` ` ``**；`shift+\`` / `/` / `f12` 全部无效 | 输入框那块 ROI 的均值：开着 **≈31–48**、关着 **≈190**（地图透出来）；无效的三个键上半屏像素差 **0.000** |
| **合成的字进得去吗** | **进得去** | 截图裁到输入框，逐字读得到 `log_ticktask_performance` / `dump_ticktask_timings` |
| **怎么提交** | **按两次回车** | 按一次：标准差 44.9 → 44.0（字一个没少、输出区一动不动）；连按两次：43.0 → **7.5**（清空）且输出区亮像素 322 → **1732** |

**"两次回车"是真原因**：第一次被控制台的**自动补全**吃掉（exe 明文里有
`SETTING_CONSOLE_AUTOCOMPLETE_MODE` / `_FULL_EXPAND` / `_PARTIAL_EXPAND` 一族设置）。
这也解释了 9/21 那次"`dump_ticktask_timings` 在 `console_history.txt` 里、文件却没出现"——
**命令执行了，但回车只被当成"接受补全"**。

### 两条仪器现在的读数

1. **`dump_ticktask_timings` → `ticktask_timings.csv`（实锤）**
   落点：**`<用户目录>\ticktask_timings.csv`**（不是 `logs/`）。
   实测一份：**573,732 B / 14,792 数据行 / 0 坏行 / 237 帧 / 256 任务**，
   表头 `frame,task,milliseconds,calls,longest_lock` 与 :data:`gametimer.TICKTASK_HEADER` 逐字一致；
   本仓的 `gametimer.ticktask_summary_lines()` 直接吃得下：

   ```
   帧 237 个（59883366 → 59884782，实测步长 [6]）；任务 256 个
   每帧各任务合计：min=3ms 中位=16ms 均值=31.43ms max=316ms
   最贵的任务：UpdateAI  帧数=237 合计=1386ms 均值=5.8481ms 最坏=70ms 最长锁=46ms
   ```

2. **`log_ticktask_performance` → `profiling.log`（仍否定，原因已查明）**
   控制台**明确回话** `Tick task logging enabled, output: profiling.log`（截图读到），
   但文件始终不出现。原因在 `platform_specific_game_data/log_settings_live.json`：
   那 26 个 logger category 里**没有 `profiling`（也没有 `ticktask`）** ⇒
   **这条日志没有 sink，等于写进空气里**。本轮按实测给它补了三个候选类别
   （`profiling` / `ticktask` / `gamemetrics`，各配一个 `file` sink，**先备份、收尾还原**），
   文件**仍然不出现** ⇒ 这条通道**暂判不可用**；不影响 G-EXIT-3，
   因为第 1 条（dump）本来就更好：**有界窗口**（`clear` → 跑 N 月 → `dump`）+ **有 frame 列**。

> 副作用（对阶段 4 侦察里那个悬案的解释）：12 份 `gametimer_*.tsv` 是旧构建产出的、
> 更新之后一份都没有 —— 现在看，更可能是"**那一类没有 sink**"而不是"启动方式变了"。
> 这一条**仍未定论**（旧构建的日志表没留存），只作为下一步的假设记着。
