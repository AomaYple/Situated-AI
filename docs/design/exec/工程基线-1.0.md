# 工程基线 1.0

本文维护工程基线 1.0 的可执行契约，落实 [工程原则](../../principles/工程原则.md)与 [贡献流程](../../../CONTRIBUTING.md)。它描述工具链入口、测试分层、产物与证据边界，不记录当前完成率，也不把离线检查写成 Victoria 3 运行期机制结论。

## 1. 测试分层

工程检查与实机验证按下表区分范围。各入口都应使用仓库 `.venv` 中的 Python，工具链在 Windows、macOS、Linux 上使用同一套 Python 入口：

| 层级 | 目的 | 常用命令 | 游戏要求 |
|---|---|---|---|
| `quick` | 语法、格式、类型和少量纯函数回归 | `python tools/ci/run_check.py lint .`、`format --check .`、`types` | 不需要 |
| `offline` | 精简快照、生成物、引用、表格和 mod 门禁 | `python tools/ci/run_check.py baseline` | 不需要 |
| `offline tests` | 排除 integration 与 benchmark 的测试，默认 pytest-xdist 并行 | `python tools/ci/run_check.py test-offline` | 不需要游戏安装 |
| `full` | 完整 pytest 收集集合，默认 pytest-xdist 并行；并行时基准用例执行不产生有效计时 | `python tools/ci/run_check.py test` | 依赖游戏文件/日志的用例按条件跳过；不等于启动游戏 |
| `live` | 窗口自动化、真实游戏推进、引擎日志和行为因果 | 专用实机脚本；`pytest -m integration` 主要核验游戏文件接口 | 需要 Victoria 3 和对应平台环境；integration 标记本身不证明 GUI 实测 |

`pytest` 的并行度由命令行和 `pyproject.toml` 的默认配置共同决定；基准测试必须显式使用 `-n0`，并清除普通测试的 `addopts`，避免把性能读数分散到多个 worker。

## 2. 离线基线

`python tools/ci/run_check.py baseline` 是本地和 CI 共用的离线闭环。它按固定顺序执行：依赖检查、快照断言、离线表格、生成物一致性、离线 modguard、离线 AI surface、离线 citations、当前 Python 源码死代码审计。任何一步失败都会保留原退出码并立即停止，方便定位第一个破坏点。

精简快照是 CI 的离线真值。快照格式版本为 `1`，必须包含 `格式版本`、`版本`、`精简` 和 `域` 四个顶层字段。精简快照和完整快照不能直接 diff；完整快照用于本机深挖，精简快照用于跨机器和跨版本门禁。

## 3. JUnit 与跳过项

CI 的普通 pytest 步骤写出 `tools/out/ci/test-results.xml`，随后由 `tools/ci/test_summary.py` 解析。摘要会输出测试总数、跳过数、失败数、错误数以及按工程类别聚合的跳过项，并保存为 `test-summary.json` artifact。

跳过原因必须能归入以下类别：`game`、`artifact`、`platform`、`tool`、`live` 或 `environment`。空原因和无法识别的原因都会让摘要步骤以退出码 2 失败，防止“被跳过”被误读成“已验证”。

## 4. 自动化状态轨迹

Windows 游戏自动化通过不可变状态轨迹记录以下阶段：

`created → foreground_ready → boot_settled → observe_selected → speed_set → running → background → verified → complete`

状态轨迹是 `SessionStart` 结果的一部分，会同时出现在结构化字典的 `automation_phase` 和 `automation_phases` 字段。它只证明自动化控制流完成了相应动作和检查，不证明 macOS/Linux 存在同等 GUI 能力，也不替代游戏机制实验。

## 5. 分析、快照和 mod 工具的稳定入口

面向 mod 开发的主要入口保持为：

- `analyze`：读取 game、jomini、clausewitz 内容根，记录脚本、defines、本地化、DLC 描述符和资源索引；
- `snapshot create|list|diff|verify`：生成、列出、自检和比较版本快照；
- `verify`：用本机游戏或入库快照核验登记断言；
- `tables`：检查生成表格是否与数据源一致；
- `modgen`：读取 `mod/decisions/fiscal.toml` 与 `mod/decisions/extensions.toml` 生成生产根级产物，新增 TOML 须显式接入；旧 `mod/data/*.toml` 只生成至 `mod/legacy/`，不进生产包；
- `modguard`：检查生成物、引用、占位符和结构门禁；
- `ai-surface`、`citations`、`preflight`、`package`：分别处理 AI 接口、来源锚定、安装前检查和交付打包。生产与 legacy 元数据及游戏版本随各自生成一致性和 Mod 门禁验证；ZIP 内容、指纹和确定性由交付测试验证。

这些命令的 `--help` 输出和核心数据结构由契约测试看守。目录重整可以改变内部实现，但不能无记录地改变这些入口的语义。

### 5.1 死代码审计

`python tools/ci/run_check.py deadcode` 调用 `tools.ci.deadcode_audit --check`，扫描 `src/pdx/`、`tools/ci/`、`tools/benchmarks/` 和 `tools/probe/` 中受控的 Python 源码。测试文件也进入引用面，避免把只由测试覆盖的接口误删；`tools/probe/frozen/` 是历史证据，不参与可删除候选。

审计基于 AST 的真实名字读取，同时登记 `__all__`、`__main__`、pytest hook、Typer/插件装饰器和类方法等动态入口。只有没有跨文件引用、同文件读取或动态入口标记的定义才会阻断门禁。报告可用 `--json` 和 `--markdown` 写入 `tools/out/ci/`，该目录是可再生临时产物，不入库。

## 6. 证据边界与未完成事项

离线测试可以证明解析器、快照、生成物和工具链在给定输入下可复现；它不能证明字段在游戏运行期的合法性、加载顺序、覆盖优先级、平衡性或 AI 因果。

当前平台证据边界仍是：Windows 有 Victoria 3 GUI 自动化证据；macOS/Linux 已验证跨平台 Python 代码、CI 和无头夹具，但没有 Victoria 3 GUI 实机证据。内存峰值和 worker 预算必须保留真实测量值；长字符串回溯优化与 2026-10-03 历史测量见 [`并行测试内存基线-20261003.md`](并行测试内存基线-20261003.md)。后续完整回归不自动更新这份内存读数。游戏运行期研究与新发现的工程维护缺口按 backlog 管理，不能混入工程基线“已完成”统计。

工具基准和端到端开发耗时只证明对应工程效率；Mod 运行性能按 [Mod 效率要求](../../principles/Mod开发原则.md#开发与运行效率)与 M4 实机出口验收。正确性修复、行为变化和性能优化分别说明，不以单个耗时数字合并结论。

实机检查点在观察者/版本/旧状态与内容稳定性检查之外，还核对同局来源报告。`pdx.checkpoint_catalog` 从完整输出 SHA 关联原局，复核现存日志、挂载、源/部署指纹和收尾；失败或缺证来源保留原件并拒绝作为干净输入。目录盘点也关联根范围内改名、复制的内容；运行器部署前核对 `saves/` 下同局来源。无关联只表示来源未知，干净来源也不提供自然机会分母或行为资格。具体用法与复制件边界见 [工具手册](../../../tools/README.md#当前处境决策实验)，拒绝演练和测量见 [M4 结果](M4-结果.md#2026-10-11-检查点来源拒绝门禁预登记)。

纯原版检查点准备采用单独来源契约：没有载入存档或探针，源码与部署集合明确为空；归档中的真实 `saves/checkpoint.v3` 必须与报告输出 SHA、头部、观察者和游戏版本一致，完整日志、挂载和恢复通过后才允许仪器重载。不能伪造 `loaded_save` 或借用 M3 行为资格。公开副本独占创建，发布失败留证据并更新准备报告，不覆写运行期间出现的同名文件。

实机和检查点准备都通过 `Deployment` 对整个用户日志目录执行持久隔离/恢复，包括子目录；原始输出按字节归档，恢复时验证原件目录与指纹。错误门禁除原有十类和 Mod 错误外，还明确拒绝 `VFSOpen Error`，实时守卫、最终归档、历史只读复核、严格比较与账本计次保持一致。新错误分类不重写历史预登记或原报告；尚未识别的错误不能据此宣称全部引擎错误均已覆盖。

## 7. 进入 mod 制作前的收口命令

Windows：

```text
.venv\Scripts\python.exe -X utf8 tools/ci/run_check.py baseline
.venv\Scripts\python.exe -X utf8 tools/ci/run_check.py test-offline
```

macOS/Linux：

```text
.venv/bin/python -X utf8 tools/ci/run_check.py baseline
.venv/bin/python -X utf8 tools/ci/run_check.py test-offline
```

按 [验证矩阵](../../../CONTRIBUTING.md#验证矩阵)选择检查；上面的离线入口不替代适用的完整回归或实机出口。游戏输入变化时先按需运行 `v3 analyze` 和 `v3 snapshot create --compact`；数据源或生成器变化时先运行 `v3 modgen --write`，再检查生成一致性与离线基线。涉及游戏运行期行为时另行记录实机环境、日志和可复核证据。
